# token 优化踩坑卡（三件套 ②）

> **读者定位**：已经开始搭六层工具链、或已经装了一半、正在被各种诡异问题折磨的人。
> **这份卡解决**：我在真实工程里踩过的坑——每条都是「现象 → 根因 → 解法」，可直接对照排查。
> **数据口径**：全部来自真实工程实践（一套百余微服务、上万 Java 文件的代码库 + 一套从零到一的资金平台）；不涉及任何客户与内部项目信息。star 为当日 GitHub API 实拉。
> **用法**：按层索引，遇到问题直接搜症状关键词。

## 🕳 通用坑（跨层）

### 坑 0：把「估算」当「实测」写进汇报/文章
- **现象**：宣传「省了 99%」「压缩 8.5 倍」，被复核时发现数字站不住
- **根因**：把「单层单次实验」外推成「全链路结论」，或计量口径错了（把 hooks 注入量当常驻全量）
- **解法**：**每条数字标注口径**（实测/估算/引用）+ 留存原始日志。真实工程里我的教训：宣传 8.5x→ 复核后真实只有 **~1.09x**（真常驻 102KB）；承认比嘴硬值钱，读者信任是攒出来的。
- **自查**：你报的数字，原始记录能调出来吗？

### 坑 1：度量数据是错的，AI 还在帮你「读」日志
- **现象**：脚本输出的「省了多少」是错的，但全流程没人发现
- **根因**：让 LLM 读日志猜数字（`rtk gain` 输出解析错，拿到的不是百分比）；或人工肉眼从大段输出里抠数
- **解法**：**数字一律用正则从结构化输出里抠**，不让 LLM 参与度量：
  ```bash
  rtk gain | grep "Tokens saved:" | grep -oE '[0-9]+\.[0-9]+%'
  ```
- **教训**：第一版度量数据错了很久——先修度量，再谈优化。

## 🕳 检索层坑

### 坑 2：`kill -9` 关 daemon，索引 store 直接坏
- **现象**：图查询报错 / 索引数据丢失
- **根因**：`kill -9` 不给 daemon 落盘机会
- **解法**：用工具的 `stop` 命令优雅关闭；万不得已 kill 后要重建索引

### 坑 3：多个项目同时 track，内存爆掉
- **现象**：机器卡死 / 索引进程 OOM
- **根因**：图索引/内存型检索（如 CBM）每 track 一个项目吃一份内存，叠加
- **解法**：**只 track 一个当前项目**；换项目先停旧的

### 坑 4：看着索引吃了几 G 内存以为出 bug
- **现象**：`ps` 看索引进程内存巨大，怀疑泄漏
- **根因**：搜索引擎 `memory` 字段是 **Go alloc（堆分配）**，不是实际常驻内存（RSS），差好几倍
- **解法**：看 RSS 不看 memory 字段；真实占用没你想的大

### 坑 5：日常写文档也开着检索索引
- **现象**：AI 每步都去查图，反而慢且费
- **根因**：索引是给「跨服务排查/大代码库检索」用的，杀鸡用牛刀
- **解法**：**写文档/小改动不开索引**；只有跨服务排查、找调用链时才启动

### 坑 6：图检索查不到，就断定「工具没用」
- **现象**：Spring 注入/反射/动态代理/注解触发（@Resource、@EventListener、@Scheduled）的间接调用，图解析不到
- **根因**：任何静态索引都有盲区，工具没骗你，是机制边界
- **解法**：流程固定为「**图查询锁 2-3 个候选 → 候选文件内 grep 精确确认**」；图查不到 → 规则里注明回退 grep 补漏，别裸奔也别全信

## 🕳 协议层坑

### 坑 7：装了压缩工具，但没验证压缩率
- **现象**：自我感觉省了，账单没变化
- **根因**：装完没跑度量，压缩率掉到 <90% 甚至失效都不知道
- **解法**：设**退化阈值**：压缩率 <90% 提醒、<85% 拉红查因（命令输出格式变了？管道没生效？）

### 坑 8：把「命令输出压缩 93%」当成「总账单省 93%」
- **现象**：对外宣称「省了 93%」，实际账单没少那么多
- **根因**：**基数错位**——压缩的是命令输出这一层，不是全部输入，更不是全部成本
- **解法**：口径永远写清楚「XX 层 / XX 维度省 YY%」；谈总账只看总输入/总花费两个数

## 🕳 散文层坑

### 坑 9：规则写在提示词里 = 许愿
- **现象**：「请简洁回答」「不要寒暄」写了，AI 照样废话
- **根因**：提示词规则是软的，模型会忘、会被上下文稀释
- **解法**：能落系统配置就落系统配置（Concise 类全局生效）；否则把风格规则放在**每次必读的核心规则**里，且规则要具体可执行（「第一行直接给结论，禁止『好的/当然/以下是』开头」）

### 坑 10：hook 里用 printf 拼 JSON，引号没转义
- **现象**：安全 hook 形同虚设，危险命令放行了
- **根因**：手动拼 JSON 时引号/转义出错，guard 逻辑没生效（只测了 `rm -rf /`，漏了 `rm -f /路径` 这种变体）
- **解法**：hook 输出 JSON 用 `JSON.stringify` 类机制而非手拼；护栏测试要覆盖**变体**，不只测教科书案例

## 🕳 生成层坑

### 坑 11：规则库越来越大，注意力被稀释
- **现象**：规则加到 15 步后 AI 反而变笨，前 3 步遵守、后面全忘
- **根因**：上下文信噪比劣化——规则互相复述、互相矛盾、越堆越多
- **解法**：**常驻内容设体积预算**（≤ 上下文窗口 5%）；**只回链、绝不复述**（细节放文件里，CLAUDE.md 只留一行指针）；30 天未触发的规则标休眠、90 天归档
- **自查**：你的常驻规则有多少行？互相重复的删掉了吗？

### 坑 12：让 AI 写「本来不用写的代码」
- **现象**：需求只要改一行，AI 顺手重构/加防御/加未来扩展
- **根因**：没给「少即是多」的生成约束
- **解法**：YAGNI 阶梯（见提示词框架模板 ③）：先给最小实现方案再写码；对「顺手优化」说 No

## 🕳 需求层坑（最贵的坑）

### 坑 13：需求含混就开始干 → 返工重写
- **现象**：一次到位率低，同一个需求反复改 3 轮
- **根因**：输入质量决定返工率——占位符式的假需求最坑（一次到位 7/8 vs 占位重写 3/8）
- **解法**：见落地清单第 ① 层 + 提示词框架模板的「需求三问」；占位符需求 = 把返工 token 提前花掉

### 坑 14：常驻指令超标，每个会话都在烧
- **现象**：会话还没干活，系统提示+工具定义已占 1 万+ token
- **根因**：harness 层塞太多常驻指令（真实案例：一个工程常驻 ~73K token，远超合理预算）
- **解法**：常驻 ≤ 上下文 5%；能放文件/按需加载的，绝不常驻；定期体检「我到底常驻了多少」

## 🕳 记账坑（贯穿全程）

### 坑 15：只看「省了多少」，不看缓存命中
- **现象**：自认为优化到位，实际省钱主因是缓存读取
- **根因**：真实账单里**缓存读取常是输入的几十倍**（我的项目：缓存读取 11 亿 token = 输入的 36.8 倍）——缓存命中率高，账单才低
- **解法**：先查缓存命中率再动手优化；**省 token ≠ 省缓存**，两个账本分开算

### 坑 16：没有回流钩子，优化效果不可见
- **现象**：优化完不知道有没有效，下个月又打回原形
- **根因**：度量做完就丢，没有持续记录
- **解法**：留存度量脚本 + 每周跑一次 + 记一张「周账单趋势表」，退化即报警

## 📌 三句话带走

1. **先修度量，再谈优化**——数字错了，优化全是自嗨。
2. **口径分清楚**——实测/估算/引用分开标；层/维度/总账分开说。
3. **规则会腐烂**——常驻设预算、定期休眠归档、只回链不复述。
