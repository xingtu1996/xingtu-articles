# 省 token 六层落地清单（三件套 ①）

> **读者定位**：已被「我是行途」系列文章种草、想自己动手把 coding agent 的 token 花销打下来的人。
> **这份清单解决**：六层工具链到底装什么、怎么配、怎么验证「真省了」——不给你玄学，给你可勾选的步骤和可复现的度量命令。
> **配套**：① 本清单 ｜ ② token 优化踩坑卡 ｜ ③ 提示词框架模板
> **数据口径**：标「实测」= 我在真实工程（一套百余微服务、上万 Java 文件的代码库）里跑出来的；标「估算」= 各层分项推算、未做交叉验证；star 为发文当日 GitHub API 实拉。**别把估算当实测用。**

---

## 〇、先记住一句话

**把「不需要 AI 推理的活」从模型手里拿回来。** 索引、检索、命令压缩、格式转换——这些是确定性的，交给工具和脚本（0 token）；只有理解、规划、写代码——这些需要推理的，才交给 LLM。

> 这一条贯穿全部六层。哪一层省得最多？检索层。哪一层门槛最低？散文层。哪一层最反直觉？生成层（让 AI 少写）。

---

## 第 0 步：先量出你的基线（不度量 = 白省）

任何优化前先记账，否则你连省没省都不知道。

```bash
# 1. 拉你的真实用量台账（Claude Code / 各工具的 usage 日志）
# 2. 记三个数：日均总输入 token、缓存读取 token、日均美元花费
# 3. 找一个「典型任务」做前后对照（同一个需求，优化前跑一次 / 优化后跑一次）
```

**基线日期**：____ ｜ **日均输入**：____ ｜ **缓存读取**：____ ｜ **日均 $**：____

> 💡 一个反直觉事实：很多人的账单里**缓存读取是总输入的几十倍**——先查你缓存命中率高不高，往往比压输入更值钱。

---

## ① 需求层：Spec 先行（省的是返工）

**原理**：输入质量决定返工率。需求写清楚，一次到位；需求含混，反复重写——返工消耗的 token 远比写清楚多。

**落地清单**：
- [ ] 开写前先答 3 问：这个任务要改什么？验收标准是什么？哪些明确**不做**？
- [ ] 复杂任务（跨文件/跨服务/多步骤）先落一个最小 spec，再让 AI 动手
- [ ] 检查你的 CLAUDE.md / 项目说明里有没有「No Spec No Code」类铁律

**省多少**：返工省下的 token 难量化（与需求复杂度强相关），但这是唯一能同时省 token 和省时间的层。

---

## ② 检索层：图查询替 grep（省的是大头）

**原理**：AI 用 grep 漫游代码库是「暴力检索」，一次要读几十上百个文件；把代码库建成图/索引，一次图查询锁 2-3 个候选，再精读。检索调用量可降一个数量级。

**落地清单（按工程规模选型）**：
- [ ] **中小单仓库 / 前端** → CodeGraph（自动同步、资源占用低）
- [ ] **Monorepo / 微服务 / 大代码库** → CBM（codebase-memory-mcp，无常驻后台、吃内存建索引）
- [ ] 代码 + 文档都要搜 → Graphify
- [ ] 巨型工程（代码文件数 > 2 万）→ 确认工具上限，超限仍要 grep 兜底

**配置要点**：
- [ ] 只 track **一个**项目，别同时开多个（内存叠加会拖垮机器）
- [ ] 索引建好后，把「先查图、锁定候选后只在候选内 grep」写进规则
- [ ] 知道工具的**盲区**：Spring 注解注入（@Resource/@EventListener/@Scheduled）、反射、动态代理这类「间接调用」，图解析经常看不到 → 规则里注明「图查询无结果时回退 grep 补漏」

**验证**（实测）：
```bash
# 同一检索任务，数两次工具调用次数：
# grep 漫游：20+ 次读取 ｜ 图查询：3-4 次 → 调用量 -74%~-80%
```

**省多少**：实测工具调用 **-74% ~ -80%**（我的工程 27 次 grep → 7 次图查询；另一套 20 次 → 3-4 次）。这是六层里**贡献最大**的一层。

---

## ③ 协议层：压缩工具输出（省的是最肥的输入）

**原理**：AI 每次执行命令，Bash 输出原样全量喂回上下文——`gradle build`、`git status` 一次几千上万 token。在「模型读到输出」之前先压缩。

**落地清单**：
- [ ] 装 rtk（命令输出压缩，实时流式）
- [ ] 高频命令（build/test/git/log）统一走压缩管道
- [ ] 验证压缩率 > 90%；若某命令压缩率掉到 <85%，查是否命令输出格式变了

**验证**（实测）：
```bash
# rtk 自带统计
rtk gain | grep "Tokens saved:"   # 正则取百分比，别让 AI 读日志猜
# 我的实测：单条命令输出压缩率 93.6%，累计 11,434 条命令省下数千万 token
```

**省多少**：实测单层 **-93.6%**（命令输出维度）。注意：这是「命令输出」口径，不是你总账单的 93.6%——别乘错基数。

---

## ④ 输入压缩层：源头瘦身（补前几层的盲区）

**原理**：检索层管代码、协议层管命令输出，但还有一大块没管：**curl 的 JSON、DB 查询结果、长文档**——这类「工具拉回来的数据」原样进上下文。在前置环节就过滤/精简。

**落地清单**：
- [ ] 盘点你的工作流里有没有「大 JSON / 大日志 / 整份文档直接喂 AI」的习惯
- [ ] 大输出先用脚本抽关键字段（jq 选列、head 限行），再喂模型
- [ ] 进阶：接输入压缩代理/层（如 Headroom 类），让压缩发生在工具与模型之间

**验证**：
```bash
# 同一条数据，压缩前后各喂一次，对比 token：
# 我的实测：本地压缩率 43.7%（2367 → 1333 token）；Read 类大文件往往是输入大头
```

**省多少**：项目宣传 20-95% 不等；我自己实测单条 **-43.7%**。这一层天花板高但工程量大，**先把「手动瘦身」习惯立起来，再考虑自动化**。

---

## ⑤ 散文层：让 AI 闭嘴（门槛最低，立刻生效）

**原理**：AI 默认话痨——寒暄、复述、解释、客套全是 token。用风格规则/系统配置让它只输出有用的。

**落地清单**：
- [ ] 写规则：回答直接给结论，不寒暄、不复述问题、不列「以下是……」
- [ ] 数字类任务强制「只给数值+单位，不解释」
- [ ] 用系统级简洁配置（如 Concise 类）或对话级风格词（如 Caveman 类：短句、电报体、去客套）

**验证**（实测）：
```bash
# 同一个问题，开/关风格规则各问一次，数回复行数：
# 我的实测：回复 185 字 → 35 字（-81%）
```

**省多少**：实测回复长度 **-81%**（n=1 小样本，但方向极其稳定——AI 客套比例天然很高）。

---

## ⑥ 生成层：YAGNI 最小代码（防「加戏」）

**原理**：AI 写代码爱加戏——防御性分支、多余封装、用不到的配置。生成前先过「少即是多」阶梯。

**落地清单**：
- [ ] 写规则：只实现需求要的，不预写未来可能用的（YAGNI）
- [ ] 生成前显式要求：先给最小实现方案，确认后再写
- [ ] 对「顺手重构 / 顺手优化」说 No，除非需求明确要求

**验证**（实测）：
```bash
# 同需求，普通生成 vs YAGNI 规则生成，对比代码行数：
# 我的实测：41 行 → 0 行（本就不该写的直接不写）；另一案例代码量 -73%
```

**省多少**：实测代码量 **-73% ~ -87%**（n=2，方向稳定）。注意：省 token 是副产物，**主产物是代码质量**——少写的代码少出 bug。

## 汇总：你到底能省多少？（诚实口径）

| 层 | 工具 | 实测（我的工程） | 口径 |
|---|---|---|---|
| ② 检索 | CodeGraph / CBM | 工具调用 -74%~-80% | 实测 |
| ③ 协议 | rtk | 命令输出 -93.6% | 实测 |
| ④ 输入压缩 | Headroom 类 | 单条 -43.7% | 实测 |
| ⑤ 散文 | Caveman / Concise | 回复 -81% | 实测（n=1）|
| ⑥ 生成 | Ponytail | 代码 -73%~-87% | 实测（n=2）|
| **综合** | — | **50-85%** | ⚠️ **估算，非实测** |

> ⚠️ **为什么综合数只是估算**：各层省的是不同基数（命令输出 ≠ 总输入 ≠ 回复长度），层间可能有重叠，**不能简单相乘**。谁跟你说「每层省 80%，五层就省 99%」，谁就是在骗你。我在自家工程先踩过这个坑：宣传数字 8.5 倍压缩，被自己复核推翻成 1.09 倍——所以这份清单里，实测和估算分得清清楚楚。
