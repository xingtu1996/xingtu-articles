# 提示词框架模板（三件套 ③）

> **读者定位**：已经装了工具，想直接抄一份「能跑」的规则/提示词，不想从零设计的人。
> **这份模板解决**：六层各自最省 token 的提示词长什么样——**全部可直接复制**，改项目名/路径即用。
> **配套**：① 落地清单（装什么/怎么验证）｜② 踩坑卡（出问题查哪）
> **说明**：规则文件因工具而异（Claude Code 读 CLAUDE.md / 其他工具读各自规则文件），模板给**通用文本**，抄进你的规则文件即可。数字与 star 为真实工程实践 + 当日 GitHub API 实拉。

---

## ① 需求层模板：开工前三问（防返工）

> 用途：任何任务开始前，先让 AI/自己回答三问。可放全局规则顶部，或作为手动检查。

```text
开工前必须确认：
1. 这个任务要改什么？（一句话说清目标与范围）
2. 验收标准是什么？（做完什么样算「对」？可验证的判据）
3. 明确不做什么？（边界：本次不做重构/不做优化/不改无关代码）

只有三点都明确，才允许开始写代码/改文件。
需求含混时：先列出你的理解 + 假设，等确认，不要直接动手。
```

**省在哪**：输入质量决定返工率。占位式需求一次到位率低（真实数据：写清需求 7/8 一次到位 vs 占位重写 3/8），返工是最贵的 token。

## ② 检索层模板：图查询优先 + 盲区兜底

> 用途：写进全局规则，让 AI 默认走图查询而不是 grep 漫游。

```text
代码检索优先级（省 token 关键）：
1. 先图查询 / 内存索引定位候选（预期 2-3 个文件），不要一上来就全局 grep
2. 锁定候选后，只在候选文件内 grep/精读确认
3. 图查询查不到时（如动态代理/反射/Spring 注解注入的间接调用）：
   → 承认图索引盲区，回退针对性 grep 补漏，不裸奔也不全信索引
4. 禁止：为找一个符号，让模型漫游式读取几十个文件

工具盲区自检：Spring @Resource/@EventListener/@Scheduled、反射、动态代理
→ 这类「间接调用」静态索引解析不到，规则里写明需 grep 补漏。
```

**省在哪**：真实实测 20+ 次 grep 漫游 → 3-4 次图查询（工具调用 -74%~-80%）。

## ③ 协议层模板：压缩命令输出

> 用途：装了 rtk 后，把高频命令统一走压缩管道，并设退化阈值。

```text
命令执行规则：
1. 高频/长输出命令（build/test/git/log/scan）一律走输出压缩管道
2. 度量用正则，不让模型读日志猜：
   rtk gain | grep "Tokens saved:" | grep -oE '[0-9]+\.[0-9]+%'
3. 退化阈值：压缩率 <90% 提醒检查；<85% 视为失效，查输出格式/管道是否被绕过
4. 口径纪律：汇报时写「命令输出压缩率 X%」，不得写成「总花费省 X%」
```

**省在哪**：真实实测命令输出 -93.6%（11,434 条命令累计省数千万 token）。

## ④ 输入压缩层模板：大输出先瘦身再喂

> 用途：任何「把外部数据喂给 AI」的动作前，先过一遍瘦身。

```text
数据喂给模型前：
1. 大 JSON：先 jq 抽关键字段（.data[].id,.data[].name），不整份喂
2. 大日志/长文档：先 head 限行 / 先 grep 关键段，再喂上下文
3. 判断标准：模型要的是「答案所需的最小信息」，不是「全部原始数据」
4. 记忆类数据（Read 结果）：只保留与当前任务相关的片段

禁止：curl 返回 63MB 的 JSON/日志原样进上下文（真实案例：这类输入是大头）。
```

**省在哪**：真实实测单条压缩 -43.7%（2367→1333 token）。

## ⑤ 散文层模板：让 AI 闭嘴

> 用途：全局生效，砍掉 AI 客套/复述/寒暄。

```text
回复风格铁律：
1. 第一行直接给结论/答案，禁止「好的」「当然」「没问题」开头
2. 不寒暄、不复述问题、不总结「以下是……」
3. 数字/状态类任务：只给数值+单位，不解释过程
4. 代码任务：只给代码+必要注释，不附「这段代码实现了……」说明
5. 被问「为什么」才展开解释；没问就默认给最短有效答案

（进阶）短句电报体风格开关：开启后 185 字回复 → 35 字（真实 -81%）。
```

**省在哪**：真实实测回复长度 -81%（n=1 小样本，方向稳定）。

## ⑥ 生成层模板：YAGNI 七级阶梯

> 用途：让 AI 写代码前先过「少即是多」阶梯，防加戏。

```text
代码生成规则（YAGNI 阶梯）：
1. 先给最小实现方案（<10 行能说清就别说 50 行），确认后再写
2. 只实现需求要求的；禁止预写「未来可能用到」的封装/配置/分支
3. 对「顺手重构」「顺手优化」「防御性增强」说 No，除非需求明确要求
4. 新依赖是重罪：加库前必须说明理由，可替代就复用现有
5. 删除比新增好：能删的代码（死代码/重复代码）优先删
6. 生成后自查：这段代码有哪一行是需求没要的？有就删
7. 度量：同一需求对比生成前后行数（真实实测代码量 -73%~-87%）
```

**省在哪**：真实实测代码量 -73%~-87%（n=2）。副产物省 token，主产物是代码质量。

## 🎁 附赠：常驻规则体检模板（防止规则腐烂）

> 用途：每季度跑一次，防止 CLAUDE.md 变成技术债（真实案例：常驻 ~73K token 超标、规则互相复述）。

```text
规则库体检（每季度）：
1. 常驻体积：当前常驻规则共多少行/token？预算 = 上下文窗口 × 5%，超了砍
2. 复述检查：同一件事是否在多个文件重复描述？（只保留一处，其余改「见 X」回链）
3. 休眠检查：哪些规则 30 天没触发？→ 标休眠移末尾；90 天没触发 → 归档删除
4. 矛盾检查：有没有两条规则互相打架？（新版覆盖旧版要删旧的）
5. 入口检查：CLAUDE.md 是否保持「一行指针 + 容器」结构，而不是全文堆砌？
```
