# 可信取数操作手册（FDE 现场版）

版本：v1.0，2026-11-12
来源案例：Miles Ma（@miles_mazy）《FDE 实战案例：可信取数（AI 工具选型与四次踩坑复盘）》，X，2026-10-30，好文集转载页 https://haowenji.com/articles/x-2115784881305161728
用途：给未来的自己在 FDE 现场做「AI 从企业数据库里查数」时直接照着执行。主干七步来自案例原文；标注「行途补充」的是结合本人电商与内容数据经验加的操作细节，可按项目调整。本手册是 001 号《多模态数据清洗操作手册》的续篇：数据洗完之后，怎么把它变成每天可查、可复核的答案。

## 0. 总原则（四条）

1. 业务问题先问明白，再让 AI 调工具。顺序反过来，模型能力再强，也可能只是更快地给出一个看起来合理的错误答案。
2. 能跑通不等于答对了。查询能执行、数字能出来，都不证明数字回答的是原来的问题；验收看的是数字对不对，不是系统跑没跑起来。
3. 一个 Tool 只负责一个明确动作，输入尽量少，计算规则固定，失败时把原因说清楚。
4. 结果必须能复核：数字后面带回原帖、评论或其他证据。分析师能抽查，报告才敢继续用。

## 1. 阶段一：先拿一个真实问题（第一步，别从万能 Agent 开始）

不要从「做一个万能查数 Agent」开始。先选一条业务每天都在问、人工已经知道怎么查的问题。

- 合格的问题长这样：「过去 30 天，某款精华在小红书和抖音上的口碑怎么样？大家主要在讨论保湿、抗老、肤感还是香味？负面评价集中在哪里？」
- 不合格的起点：「做一个能查所有数据的智能体」「接一个万能问答」——没有真实问题打底，Tool 的输入定义无从写起。
- 行途补充：先跟业务团队跑一次人工查数的全过程，记下他们在页面上点的每一步、每一步的判断依据——这份记录就是后面 Tool 输入定义的初稿。

## 2. 阶段二：根据数据和用法选数据库

选型口径（案例原文）：

| 数据与用法 | 放哪里 |
|---|---|
| 结构稳定、关系明确的数据（项目、用户、权限、订单） | PostgreSQL 等关系型数据库 |
| 需要反复搜索和统计的帖子、评论；内容多、来源多、查询方式经常变化 | ES |
| 图片、音频、视频等原始文件 | 单独保存，不进 ES 也不进关系库 |

选型纪律：数据库怎么选，先看数据是什么样，再看人准备怎么用。不要先定技术再套业务。

## 3. 阶段三：把问题里没说出口的条件补齐（需求五问）

任何一句业务问题，落到查询里之前先过五问，缺一项就回去问业务，不要猜：

1. 查哪个对象（哪款产品、哪个品牌；同一产品有多个叫法时以哪个为准）；
2. 看哪个时间（时间按发布时间算，还是按系统采集时间算）；
3. 从哪些来源取数（哪些平台；只看原帖，还是帖子和评论一起看；图片文字、视频口播和正文要不要一起搜）；
4. 用什么指标（声量数帖子、评论、用户还是具体观点；负面看整篇内容，还是看用户对具体体验的评价）；
5. 最后要不要把原帖证据一起带回来（给谁看、拿它做什么判断）。

五问的写法：写成一张表贴在需求文档开头，每问一行，写清业务的原话和最终定下来的口径；口径变了就改表、留版本，不要只改查询。

行途补充：五问里最容易漏的是第 4 问——业务词多义。「声量」「热度」「负面口碑」这类词，每个人心里算法不一样；第一次听到业务词，先问「你说的声量，具体怎么算」，再动手。

## 4. 阶段四：用真实难例测试

以下四类情况必须专门测，测不过不放行：

- 一篇内容提到多个产品（例：用户说精华 A 保湿不错、精华 B 太黏，系统不能把这篇算成精华 A 的负面口碑）；
- 同一产品有多个叫法（全名、简称、系列名、用户自己的叫法）；
- 帖子和评论同时出现（评论的情感归属要回到原帖和上级评论判断，不能只看单条）；
- 时间与范围边界（漏平台、选错时间范围、把评论和原帖混在一起）。

测试方法：准备一批人工确认过的难例样本，含正常数据和容易出错的案例；每次换规则、换模型、换 Tool 定义，用同一批样本重跑一遍再放行。

验收红线（案例原文口径）：查询树与聚合树是两件事——查询树决定「哪些数据能进来」，聚合树决定「这些数据怎么算」。只保证查询不报错远远不够；条件选对了，统计方法仍可能选错，两边都要测。

## 5. 阶段五：把高频需求做成 Tool

一个 Tool 只负责一个明确动作。设计模板（以「查询产品口碑」为例）：

- Tool 名称：一个动词加一个对象，如「查询产品口碑」「比较竞品趋势」「找出负面讨论增长最快的话题」；
- 输入（只留 AI 必须确认的项，越少越好）：查哪款产品、看哪几个平台、时间范围是什么、按帖子、评论还是人数统计、要不要带回原帖证据；
- 留在 Tool 内部处理、不暴露给模型的事：产品在系统内部叫什么、查询该怎么执行、结果为空时怎样判断原因；
- 输出：数字 + 对应原帖/评论证据 + 计算口径说明；
- 失败时：把原因说清楚（缺哪个条件、哪个范围为空、为什么算不出来），不要只返回空值。

行途补充：Tool 清单先写在一张表上，每行一个 Tool、一句话说明它负责什么、输入有哪几项；新需求先查表——已有 Tool 能覆盖的不要新造，只在确实没有时才加。

## 6. 阶段六：通过 MCP 交给 AI 调用

MCP 是一套让 AI 发现和调用这些 Tools 的通用方式，相当于给 AI 一张工具菜单：有哪些工具、每个工具是干什么的、需要填写什么。AI 根据业务问题选工具，再补齐有限的几个条件。

分工口径：AI 负责理解问题和选择工具，内部查询交给 Tool 完成。让 AI 做选择题，不要让它临场写一份没有标准答案的程序。

红线（案例原文）：接上 MCP 不会自动让数据变准。MCP 负责把工具交给 AI，Tool 里面的业务规则仍然要有人定义。菜单解决的是「怎么调」，不是「调得对不对」。

## 7. 阶段七：结果必须能复核

- 数字后面带回原帖、评论或其他证据；分析师能抽查，报告才敢继续用。
- 复核动作：抽查时按证据回到原文，核对对象、时间、来源、算法四项与五问表是否一致。
- 报告纪律：没有证据的数字不进正式报告；证据链断了的数字先标待核，不参加精确数值统计。

## 8. 四种取数办法的选型对照（按代价排序）

| 办法 | 适合 | 不适合 | 典型失败模式 |
|---|---|---|---|
| AI 直接写查询 | 快速验证 | 日常报告、稳定运行 | 多产品同帖误判情感归属；漏平台、选错时间、评论原帖混淆；条件对了统计方法仍可能错 |
| 查询固定模板 | 格式稳定、反复测试 | 业务词多义的场景 | 「声量」三种算法都说得通，模板默认一种时稳定地给出不符合需求的数字 |
| Computer Use 点页面 | 演示、偶尔查一次 | 日报、周报、竞品切片连续跑 | 旧筛选没清掉、页面未加载完就读结果，读到上一轮的旧数字且不自知；按钮换位置、加载变长、中途断掉恢复成本高 |
| 直接调业务 API | 执行快 | 让模型补上下文 | API 是给前端用的，模型要自己补齐项目、数据源、字段和组合规则；少条件返回空值，填错条件得到看似正常、实际无用的数据 |

选型纪律：先把失败模式写出来，再列优点；演示第一轮顺利证明不了能跑日报，验收至少连跑三轮，看旧条件清没清干净。

## 附：一页速查

真实问题（每天都在问、人工会查）→ 选库（关系库放结构数据、ES 放搜索统计、原始文件单独存）→ 五问补齐（对象、时间、来源、指标、证据）→ 难例测试（多产品同帖、多叫法、帖评同现、边界条件；查询树与聚合树都要测）→ 做成 Tool（一个动作、五项输入、失败说清原因）→ MCP 调用（AI 做选择题）→ 结果复核（数字带回原帖证据）。
