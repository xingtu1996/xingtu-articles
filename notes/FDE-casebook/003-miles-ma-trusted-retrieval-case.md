## 一句话

数据洗干净之后，客户每天都要问的口碑问题怎么答得准：把一句「某款精华过去 30 天口碑怎么样」先拆成五个没说出口的条件，再试过四种取数办法，最后把高频需求做成一个输入只有五项的 Tool，让 AI 选工具而不是现场写查询——可信取数的关键不在模型，在业务定义。

## 原文结构（精华转述）

需求五问 → 为什么用 ES → ES 宽文档的坑 → 四次尝试（直接写查询 / 固定模板 / Computer Use 点页面 / 直接调业务 API）→ 回到 MCP 和 Tools → FDE 到底做什么 → 七步可执行清单 → 预告下一篇（Agent 分步执行与查询失败重规划）。

- 需求五问：客户原话是「看过去 30 天，某款精华在小红书和抖音上的口碑怎么样？大家主要在讨论保湿、抗老、肤感还是香味？负面评价集中在哪里？」落到查询里至少先确认五件事：查哪个对象、看哪个时间、从哪些来源取数、用什么指标、最后要不要把原帖证据一起带回来。任何一项没说清楚，系统都给不出正确的答案。客户要的不是临时查一次，而是稳定的每日运行：以后遇到类似问题，AI 能自己查数，结果还要稳定、准确，最好能把对应原帖一起带回来。
- 为什么用 ES：PostgreSQL 这类关系型数据库适合存项目、用户、权限、订单等结构稳定、关系明确的数据；ES 适合内容多、来源多、查询方式经常变化的场景（今天搜某款精华口碑，明天比两个品牌，后天追一条突然上升的负面话题）。分工口径：图片、音频、视频等原始文件单独保存；项目和权限等业务信息放关系型数据库；需要反复搜索和统计的帖子、评论放进 ES。数据库怎么选，先看数据是什么样，再看人准备怎么用。
- ES 宽文档的坑：一条社媒内容在 ES 里不是一行表格，而是一份很宽的文档——原帖之外还有发布用户、图片 OCR、视频 ASR、品牌和产品、评论关系、互动快照、模型生成的标签，业务越往后做字段越多，一条记录几百个字段很常见。难处不只是字段多，而是很多字段长得相似、业务意思却不一样。问「精华 A 的负面评价」时还要判断五件事：负面说的是整篇帖子还是帖子里对精华 A 的具体评价；时间按发布时间还是采集时间算；只看原帖还是帖子和评论一起看；图片文字、视频口播和正文要不要一起搜；最后的声量数帖子、评论、用户还是具体观点。AI 选错一个位置，查询照样能执行、结果照样有数字，只是回答的已经不是原来的问题。
- 第一次尝试，让 AI 直接写 ES 查询：业务人员提问题，AI 根据数据说明生成查询，再去 ES 拿结果。简单问题能跑（「查过去 30 天提到精华 A 的帖子」）；难在「查精华 A 的负面评价」：一篇帖子同时提到两款产品，用户说精华 A 保湿不错、精华 B 太黏，AI 只看到「帖子里出现了精华 A」和「帖子里有负面评价」，就可能把这篇算成精华 A 的负面口碑，这类数量特别多，一旦统计错结果很可怕。条件一多还可能漏平台、选错时间、把评论和原帖混在一起。结论：适合快速验证，直接拿去做日常报告风险太高。更隐蔽的一类问题：查询条件选对了，统计方法仍可能选错——先筛出提到精华 A 的内容再统计整篇帖子情感，和直接统计「用户对精华 A 的具体观点」，负面比例可能完全不同。一条 ES 查询里同时有两件事：查询树决定「哪些数据能进来」，聚合树决定「这些数据怎么算」。只保证查询不报错远远不够。
- 第二次尝试，把查询写成固定模板：产品、平台、时间等常用条件做成固定模板，AI 不再临时拼一整段查询，只要填几个选项。查询格式稳定了，同一类任务也方便反复测试。但模板能固定动作，固定不了业务的意思：业务说「看一下这款精华的声量」，有人只算原帖，有人把评论一起算，还有人更关心参与讨论的人数——三种算法都说得通，结果却不是一回事。模板默认数原帖而客户想看帖子加评论时，系统会很稳定地给出一个不符合需求的数字。结论：查询变稳了，业务问题仍然可能理解错。
- 第三次尝试，让 AI 像分析师一样点页面（Computer Use）：AI 打开现有分析系统，选项目、产品、平台，设时间，再读页面结果。好处是现有系统直接复用、暂时不用改后端，做演示或偶尔查一次很直观。麻烦是步骤太长：上一轮查品牌 B、这一轮查精华 A，旧筛选可能没完全清掉；或者页面还在加载，AI 已经开始读结果——最后拿到的数字看着正常，其实混进了上一轮条件或读到旧结果。页面按钮换位置、加载变长、执行中途断掉，都会增加恢复成本。现场测试第一轮往往很顺，真正麻烦的是第二轮和第三轮：旧条件有没有清掉、页面到底加载完没有，AI 很难像熟练分析师那样随时察觉；一旦读到旧数字，它也未必知道自己错了。结论：偶尔用一次没问题，要连续跑日报、周报和竞品切片会越来越慢。
- 第四次尝试，直接调用现有业务 API：速度快了很多，AI 不用打开页面，直接把查询交给业务系统。但原来的 API 是给前端程序用的：页面知道用户在哪个项目、选的是哪份数据、每个按钮对应什么；AI 只拿到一句「查精华 A 的负面口碑」，这些背景都不知道。原文的比喻：一家餐厅的收银系统，店员按一下「招牌套餐」，系统知道后面对应哪些商品和价格；把收银系统的内部操作直接交给一个第一次来的外人，他看到的全是系统自己的暗号，很难每次都填对。业务 API 执行得很快，但它没有按照 AI 容易理解的方式设计。测试结果：接口速度没问题、系统也能返回数据，但模型要自己补齐项目、数据源、字段和组合规则；前端原来替用户记住的上下文，现在全要模型猜——少一个条件可能返回空值，填错一个条件也可能得到一份看似正常、实际毫无用处的数据。
- 最后为什么回到 MCP 和 Tools：Tool 就是 AI 可以调用的一个具体动作，如「查询产品口碑」「比较竞品趋势」「找出负面讨论增长最快的话题」，每个 Tool 都提前写清楚需要哪些信息、最终返回什么。以「查询产品口碑」为例，AI 只需要确认五项：查哪款产品、看哪几个平台、时间范围是什么、按帖子、评论还是人数统计、要不要带回原帖证据；产品在系统内部叫什么、查询该怎么执行、结果为空时怎样判断原因，都留在 Tool 里面处理。MCP 是一套让 AI 发现和调用这些 Tools 的通用方式，相当于给 AI 一张工具菜单：有哪些工具、每个工具是干什么的、需要填写什么；AI 根据业务问题选工具，再补齐有限的几个条件。这比让 AI 自己写一整套查询简单得多：前者像做选择题，后者像让它临场写一份没有标准答案的程序。但接上 MCP 不会自动让数据变准——MCP 负责把工具交给 AI，Tool 里面的业务规则仍然要有人定义。
- FDE 在这里做的到底是什么：客户说「我要看精华 A 的负面口碑」，FDE 要继续往下问：这份数据最后给谁看？他要拿它做什么判断？负面看整篇内容，还是看用户对具体体验的评价？一篇帖子里提到两款产品怎么办？数字出来以后，要不要附原帖让分析师复核？这些问题先说清楚，才能把「查询产品口碑」做成一个真正可用的 Tool。结论句：FDE 先处理业务问题，工程实现排在后面。业务需要什么，就把它拆成 AI 能理解的条件，再把这些条件交给工具执行；MCP 是中间的连接方式，真正决定结果能不能用的，还是前面的业务定义。
- 七步可执行清单（原文结尾）：一，先拿一个真实问题——不要从「做一个万能查数 Agent」开始，先选一条业务每天都在问、人工已经知道怎么查的问题；二，根据数据和用法选数据库——结构稳定、关系明确的数据优先放 PostgreSQL 等关系型数据库，需要搜索大量内容、频繁换条件统计时再考虑 ES；三，把问题里没说出口的条件补齐——查谁、查什么、怎么算、结果给谁用，都要写清楚；四，用真实难例测试——一篇内容提到多个产品、同一产品有多个叫法、帖子和评论同时出现，这些情况都要专门测；五，把高频需求做成 Tool——一个 Tool 只负责一个明确动作，输入尽量少，计算规则固定，失败时把原因说清楚；六，通过 MCP 交给 AI 调用——让 AI 负责理解问题和选择工具，内部查询交给 Tool 完成；七，结果必须能复核——数字后面带回原帖、评论或其他证据，分析师能抽查，报告才敢继续用。收束句：先把业务问题问明白，再让 AI 调工具；顺序反过来，模型能力再强，也可能只是更快地给出一个看起来合理的错误答案。
- 下一篇预告：Tools 做好以后，Agent 怎么分步执行，查询失败以后又该怎么重新规划。

## 与行途经验的对照

| 维度 | 案例做法 | 行途既有经验 | 启发 |
|---|---|---|---|
| 验收观 | 数字后面必须带回原帖证据，分析师能抽查报告才敢用 | 「完成认凭证不认自述」 | 同一条纪律的两个版本：交付认凭证，取数认原帖证据；001 号的证据分级到这里落成验收动作 |
| 工作顺序 | FDE 先处理业务问题，工程实现排在后面；业务定义决定结果能不能用 | 写过「Harness 是规矩不是工具」、护栏三段论 | 规矩先行再添一现场证据：Tool 的输入定义就是取数侧的护栏 |
| 成本观 | 高频需求做成 Tool、输入尽量少，模型只做理解问题和选工具 | 「省 token 的第一性原理：把不用推理的活从模型手里拿回来」 | 同一条分工：查询执行不该由模型临场写，交给 Tool |
| 复用观 | 一个 Tool 只负责一个明确动作；MCP 是工具菜单，AI 做选择题 | 「一个 Skill 干所有事？我把它拆成了流水线」 | 拆法同理：Tool 是流水线上的单步，菜单化后才可复用、可测 |
| 失败观 | 四种办法各有明确的失败模式与适用边界（快速验证可用、日报不可用） | 视频管线红线「技术指标通过 ≠ 实际合格，必须看一遍成片」 | 失败模式要写进验收：查数能跑通 ≠ 数字是对的，难例测试就是取数侧的「看一遍成片」 |
| 场景迁移 | 美妆口碑查询 | 本人本职电商技术，多平台评论/晒单/直播回放是同一类数据 | 同一条链路的第二段：001 号洗完的数据，到这里变成每天可查的口碑；电商场景照搬五问与 Tool 五输入即可 |

## 对第二曲线的价值判断

- 可迁移性：高。取数是行业无关的现场能力，任何「AI 从企业数据库里查数」的场景都先过五问再动手；与 001 号的清洗链路连起来，构成「洗数据 → 查数据」的一条完整交付线。
- 可沉淀资产：需求五问、Tool 设计五输入、七步可执行清单、四种取数办法的失败模式对照——已沉淀为操作手册 v1.0（同目录），下个项目直接套用。
- 可报价性：适合按交付物报价（可复核的查询能力 + Tool 清单 + 难例测试集），不按人天卖时间；与 001 号「按数据集报价」的判断同属一条线。
- 局限：原文是一家之言且无量化效果（四种办法各跑了多久、花了多少人力、准确率变化均未给），引用只引方法、不引效果；MCP/Tool 的具体实现细节原文未展开，按现场再定。
