# 多模态数据清洗操作手册（FDE 现场版）

版本：v1.1，2026-10-28（v1.0 同日先行版依据先行摘要编写，v1.1 已按原文全文逐项核对更正）
来源案例：Miles Ma（@miles_mazy）《FDE 实战案例｜数据清洗》，X，2026-10-27，https://x.com/miles_mazy/status/2115006510979801566
用途：给未来的自己在 FDE 现场做多平台评论/舆情类数据清洗时直接照着执行。主干八步来自案例原文；标注「行途补充」的是结合本人电商与内容数据经验加的操作细节，可按项目调整。

## 0. 总原则（四条）

1. 原始内容永远保留：清洗、识别、打标都只新增结果，永不覆盖原文原文件。
2. 规范先行：没定规范之前不清洗。删除不可逆，标记可逆——能标记的绝不先删。
3. 冲突看证据等级，不看模型置信度；裁不了的进待核队列，不进精确统计。
4. 全程留痕、按版本入库：任何一步的结果都要能查清「在哪一步、被什么规则/模型、因为什么」变成现在这样。

## 1. 阶段一：定数据规范（第一步，先问用途）

进场先问业务团队一句：这批数据最后拿来干什么？不同用途对应不同清洗方式，先把差异列清：

- 舆情报告：看事件、传播、风险；
- 竞品报告：比品牌、产品线、功效、成分、用户评价；
- 营销复盘：看渠道、内容、互动、反馈；
- 评论分析：额外保留用户提问、上下文与回复关系。

规范文档必须写清五件事：哪些字段必须保留；帖子、评论、用户如何关联；哪些判断必须附带原文证据；哪些数据可直接使用；哪些数据需要人工确认。

关键判断（案例原文）：同一素材被多个账号发布，传播复盘要全保留、自然讨论统计要标同一重复组。先标记、后统计，口径随时可换；先删除，口径永远换不了。

## 2. 阶段二：原始内容保留

必须留存：原文、原图、原音频、原视频、链接、发布时间、平台原始 ID、采集时间。
存放纪律：原始层只读；清洗后文本单独存；OCR/ASR/模型标签作为新增结果挂在原始记录上。

## 3. 阶段三：梳理数据关系

单平台内至少保留四类 ID：

| ID | 含义 |
|---|---|
| user_id | 谁发布了内容 |
| post_id | 评论属于哪条原帖 |
| comment_id | 当前是哪条评论 |
| parent_comment_id | 这条回复在回应谁 |

主键建议写成「平台名 + 平台原始 ID」，避免跨平台编号撞车。
跨平台纪律：不直接认人。昵称相同、头像相似只算线索；没有可靠主键和明确授权，只汇总话题、对象、内容，不拼个人轨迹。一句话：平台内理清关系，平台间分开保存来源。

## 4. 阶段四：多模态归一（分开处理，统一格式）

统一目标格式：谁、在什么时间、说了什么、提到了什么对象、证据在原内容的哪个位置。

- 文字：保留原文；处理乱码、空白、链接、语言、重复段落；模型提取观点时必须同时返回对应原句。
- 图片：OCR 提取价格、型号、日期、截图文字；视觉模型识别对象、场景、部件；两种结果都保留图片位置，便于判断文字与对象是否同属一个区域。
- 音频：先统一格式与采样率再 ASR，输出带时间码；多人对话才加说话人区分，普通口播不加这层。
- 视频：拆音轨与关键帧，音轨 ASR、关键帧 OCR 与视觉识别，按时间合并；不逐帧分析，先低频抽帧加全文转写定位相关片段，再对局部提高抽帧密度。

工具选型（案例原文的常见组合）：FFmpeg 拆音轨/转码/抽帧；PaddleOCR 做本地 OCR；Whisper 做本地语音识别；云端可接百度智能云 OCR、腾讯云 OCR、腾讯云 ASR、火山引擎字幕生成。
选型顺序：小批量先用 API 验证，数据量稳定后把高频任务搬本地。比价之外，必须拿自己的真实样本测五项：方言、噪声、中英混合、竖屏字幕、截图小字。额度与并发限制上线前以控制台为准。
行途补充：任务会反复执行时，搭一个轻量工作台（文件/链接进入 → 自动选工具 → 原文与识别结果对照 → 人工修正 → 导出 JSON/CSV），并记录每次调用的次数、耗时、费用、失败原因。跑一段时间，哪些环节该本地化自然有答案。

## 5. 阶段五：冲突与质量清洗

### 5.1 证据分级（冲突裁决的依据）

| 等级 | 内容 |
|---|---|
| A | 官方字段或人工确认结果 |
| B | 原图、原音频、原视频中可直接确认的内容 |
| C | 多个模型结果一致，且上下文能对上 |
| D | 单个模型的识别或判断 |
| E | 关键词、正则、简单规则给出的候选值 |

冲突处理流程：按时间码和图片位置回到原始证据 → 核对单位、上下文、发布时间 → 能确认则修正；确认不了进待核队列，不参加精确数值统计。
修正留痕字段：原始值、修正值、证据等级、修正原因、复核状态、模型版本。原值永不覆盖。

### 5.2 相关性筛选
关键词与词典负责尽量找全，语义模型补充简称、缩写、相近说法。

### 5.3 重复处理
完全复制、轻微改写、同图不同文、同视频再发布，归入同一个重复组。原始记录保留，统计时再决定按帖子、素材还是账号去重。

### 5.4 异常识别与四种状态
判断信号：发布时间、内容相似度、账号历史、发帖节奏、互动网络。
每条记录最终输出四种状态之一：正常可用 / 重复关联 / 低质量（等待修复或隔离） / 高风险（进入人工复核）。
红线：风险分只负责把可疑内容排到前面。活动统一素材、媒体矩阵、合作账号也会高度相似，看见高分不许直接删除。

## 6. 阶段六：生成结构化数据

结构化分五类落字段：谁在表达、评价对象是谁；提到了什么产品、部件、功能或服务；对象之间发生了什么；用户的观点、问题和意图；判断依据是哪句原文、哪个图片位置、哪段音频。
只打一个情感标签的数据后面几乎没法用，这是本阶段存在的理由。

分工：高频、规则稳定的任务交给规则和小模型；多语种、多对象、复杂指代、长文本交给大模型；低置信结果进人工复核。
大模型输出纪律：按固定 JSON 格式返回字段和证据；字段名、可选值、空值规则提前写清，输出才能直接验收和入库。

## 7. 阶段七：验收

入库前检查清单：原始内容和链接是否完整；评论能否回到原帖和上级评论；OCR/ASR/视觉结果是否带位置；冲突是否有处理状态；标签是否绑定正确对象；规则、模型、字段是否有版本号。
回归机制：准备一批人工确认过的测试样本，含正常数据和容易出错的难例；每次换规则、换模型，用同一批样本重跑一遍再放行。

## 8. 阶段八：按规则和版本入库

入库时四类分开保存：原始数据、处理结果、质量状态、版本信息。这样才能重新处理、对比新旧结果、定位每条数据在哪一步发生了变化。

完整交付七件套：数据字典、关系说明、处理流程、质量报告、难例集、复核队列、版本记录。

## 9. 常见坑（按代价排序）

1. 采集后直接删重复——统计口径再也换不了；
2. 只存模型加工结果——出错时分不清错在采集、识别还是分析；
3. 跨平台凭昵称头像拼人——合规和准确性一起出事；
4. 冲突时按置信度裁决——错误数字一路进报告；
5. 看见风险高分就删——活动统一素材和合作账号会被误杀；
6. 视频逐帧分析——成本爆炸且没必要，先定位片段再加密抽帧；
7. 只打情感标签不落字段——数据洗完还是没法查询使用；
8. 每个业务各洗一遍——三套口径三个数，复盘时必然打架。

## 附：一页速查

定规范（问用途、五件事写清）→ 原始全保留（只新增不覆盖）→ 连关系（四类 ID、跨平台不认人）→ 多模态归一（分开洗、统一格式、先 API 后本地）→ 冲突与质量（证据 A–E 分级、待核队列、重复进组、异常排序复核）→ 结构化（五类字段、规则与模型分工、JSON 定格式）→ 验收（检查清单 + 难例集回归）→ 版本入库（四类分存、交付七件套）。
