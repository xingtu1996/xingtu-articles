## 二、现场提到的三种路线对比

| 维度 | 传统 RAG（切片+向量） | PageIndex / DayIndex | AnySearch |
|---|---|---|---|
| **做法** | 文档切块→向量化→检索 top-k | 不切片不向量，LLM 读全文→生成 markdown 目录→查询时把所有目录喂给模型判断 | 现场只提了名字，未展开 |
| **检索逻辑** | 语义相似度匹配 | 模型读目录做文件级筛选 | 未知 |
| **效果** | 够用，生产验证过 | 确实好一些（但只"一点点"提升） | 未知 |
| **入库成本** | 低（embedding 便宜） | **一份文档 50 分钟，全是 LLM 分析，非常贵** | 未知 |
| **适合规模** | 几十 GB ~ TB 级 | **小样本验证可以，几个 T 的数据用不起** | 未知 |
| **现场结论** | 继续用 | 验证完放弃了——"集团有几个 T 的怎么办？算了吧" | 待验证 |

### PageIndex / DayIndex 原理（现场描述）

1. 不做项目切分、不做切片、不做向量化
2. 把一个很长的文件让大模型读一遍
3. 大模型给这个文件写一个目录（markdown）
4. 这个目录作为下次检索时的纯文本索引
5. 假设 100 个文件 = 100 个 markdown 代表这 100 个文件
6. 查询时把这 100 个目录全喂给模型，让模型判断哪个文件里可能有相关信息
7. 再深入读相关文件

**本质**：用 LLM 做"文件级路由器"，而不是向量做"chunk 级匹配"。

## 三、RAG 技术路线全景（三代演进）

> 现场讲者说"上百种技术线"，归纳下来就是三代+几个变体。

### 第一代：Classic RAG（经典向量检索）

- **核心动词**：retrieves（检索）
- **做法**：文档切块 → Embedding → 向量库 → 查询时语义匹配 top-k → 拼上下文喂 LLM
- **优点**：成熟、便宜、生产验证充分
- **缺点**：chunk 丢失全局上下文；跨文档/跨章节问题答不了；需要反复调 chunk size
- **行途素材库现状**：现阶段用的就是这一代（全文搜索/向量）

### 第二代：GraphRAG（知识图谱增强）

- **核心动词**：connects（连接）
- **做法**：LLM 从文档中抽取实体和关系，构建知识图谱；查询时沿图谱做多跳推理
- **代表**：微软 GraphRAG（开源）
- **擅长**：全局感知问题——"整个文档集里有哪些主题？""A 公司和 B 公司是什么关系？"
- **不擅长**：纯事实查找（比向量慢且贵）
- **现场对应**：讲者说的"各种图"就是 GraphRAG

### 第三代：Agentic RAG（智能体自主检索）

- **核心动词**：reasons（推理）
- **做法**：LLM 自己决定检索策略——简单问题直接答，复杂问题多轮检索、改写查询、判断要不要换检索源（向量库/图谱/数据库）
- **代表**：LangGraph + RAG、自适应 RAG
- **特点**：准确率比固定流水线高 40%，但 token 消耗也高
- **趋势**：RAG 不再是一个"组件"，而是一个可组合的检索工具箱 + Agent 调度

### 关键变体：Contextual Retrieval（上下文感知检索）

- **做法**：切片后、Embedding 前，先用轻量 LLM 给每个 chunk 加一段全局上下文摘要（如"这段来自《XX报告》第三章，描述了防火墙策略 3.2 节"），再 Embedding
- **效果**：检索准确率显著提升（Anthropic 实测幻觉率降 49%）
- **本质**：解决"chunk 脱离上下文看不懂"的问题——和 PageIndex 思路同源，都是"用 LLM 给文档加结构"

### 关键变体：PageIndex / LLM Wiki（现场提到的）

- 详见第二节。本质是把"文件级目录生成"从 chunk 级上移到文件级
- 和 Contextual Retrieval 的区别：Contextual 是给每个 chunk 加上下文；PageIndex 是给整个文件生成一个 markdown 索引页

## 四、开源 RAG 平台/工具对比

> 不自己写 RAG 管道，直接用开源平台的话，主流四选：

| 平台 | 一句话定位 | GitHub Star | 最擅长 | 部署要求 | 适合谁 |
|---|---|---|---|---|---|
| **Dify** | LLM 应用开发平台（Workflow+RAG+Agent） | 142k | 工作流编排、多模型兼容、低代码 | 2C4G 起 | 有研发能力的团队，做多种 AI 应用 |
| **RAGFlow** | 深度文档理解 RAG 引擎 | 80k | OCR+表格结构化、引用溯源、复杂文档 | 4C16G 起 | 法律/医疗/合同等复杂格式文档问答 |
| **FastGPT** | 轻量知识库问答 | 25k | 开箱即用、30 分钟搭好、中文优化 | 2C8G 起 | 小团队快速搭客服/知识问答 |
| **MaxKB** | 开源知识库问答系统 | — | 简单、轻量 | 低 | 个人/小团队基础知识库 |

**选型速判**：
- 只是想快速搭个知识库问答 → FastGPT
- 要处理合同/扫描件/表格这种复杂文档 → RAGFlow
- 要做完整的 AI 应用（不止问答，还有工作流/Agent） → Dify
- 自己写代码搭管道 → LlamaIndex / LangChain + 向量数据库

## 五、和行途素材库的映射

这套现场经验直接对应当前行途素材库的 RAG 选型：

| 现场教训 | 行途素材库对应 |
|---|---|
| 新方案"性感但贵"，必须小规模验证再上 | 素材库先用传统全文检索/向量，不急着上 LLM Wiki |
| PageIndex 入库 50 分钟/文档 | 如果素材库涨到几百篇文章，LLM 生成目录的成本要算 |
| "不帮他验证他一直惦记" | 自己也会被新方案种草，先小规模跑通再全量 |
| 向量切片是生产验证过的 baseline | 行途素材库现阶段文件量（<200 篇），直接全文读+语义搜索就够 |
