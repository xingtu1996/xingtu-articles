# Anthropic官方提示词手册：Fable 5.1的12条模式

有时候停下来想想：我用了这么久Claude，提示词写了一堆，但模型一升级，老提示词还管用吗？

最近Anthropic给Fable 5.1出了一份官方提示词文档，开篇就说：老提示词不用改，也能用。但要补的是它新长出来的脾气——变安静、变克制、变省。

官方文档列了十几条行为差异，你不用全读——这篇把里面最能解决问题、最能提升效率的部分汲取出来：12条官方模式，每条附能直接抄的英文prompt原文，一字没改。

这篇把最实用的几条讲透，告诉你哪些该加、哪些旧禁令该删。

## 1. Fable 5.1变了什么

三个核心变化：

变安静：长工具链里，5.1默认比前代更沉默，effort越高越明显。你会看到它安静好几分钟，最后一条消息还只讲最后一步。

变克制：加粗用得更少，也更不愿意用标题、列表和引号。以前的模型爱堆项目符号和加粗，很多提示词里至今留着"少排版"的禁令——这些旧禁令该删了。

变省：小改动别重写整个文件，长输出别在草稿上耗光预算。5.1动笔前会想更久，一次请求要长交付物时，它可能先在思考里写一遍，再作为回复重写一遍——更慢也更费。

## 2. 最实用的5条模式

### 模式一：自主推进（无人值守核心）

这是12条里最重要的一条，直接决定了Claude能不能在你不盯着的时候自己把活干完。

官方原文：

> You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking "want me to...?" or "Should I...?" will block the work. For reversible actions that follow from the original request, proceed without asking. Stop only for destructive actions or genuine scope changes the user must decide. Offering follow-ups after the task is done is fine; asking permission before doing the work is not.

翻译过来就是：你正在自主执行任务。用户没有实时盯着，也无法在任务中途回答问题——所以问「要不要我继续」会把工作卡住。凡是原始请求衍生出的可逆操作，直接做完，别问。只有破坏性操作或真正的范围变更，才需要用户拍板。任务做完后的后续建议可以有，干活前请求许可不行。

开头那句"用户没在实时盯着"承担了大部分效果，原样保留。

![配图_自主推进模式图.png](配图_自主推进模式图.png)

### 模式二：交付范围

你要的范围就是交付范围。

官方给了两段，建议一起用。核心是：Claude有时会描述下一步而不去做（"接下来我会..."），或者为原请求已经涵盖的步骤停下请示（"要我应用吗？"）。

加上这条后，它会把你请求范围内的事一次性做完，不会做一半停下来问你。

### 模式三：进度叙述

让它边干边说。

5.1默认比前代更沉默，长工具链里你会看到它安静好几分钟。先确认你的客户端真的在接进度块，再把提示词里"所有发现留到最后再说"这条旧禁令删掉。

还想要更多，就明说你要什么。比如："每完成一个步骤，用一句话告诉我进展。"

### 模式四：反文艺腔

把套话摁下去。

5.1的文字整体比前代更好，套话和不解释的黑话都更少。但有时它的句子会更长、段落更少，读起来发闷。

管用的做法是把要反对的东西定义清楚，放进用户消息（更优）或系统提示。官方给了段"矫饰文风"的定义原文：

> Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning."

翻译：矫饰文风用隐喻和修辞替代直接表述——本该说"一个值得调整的参数"，它写成"一个值得拧动的旋钮"。嫌长也有极简版：Please remove all mannered prose.

### 模式五：小改动别重写整个文件

5.1比前代更容易为一处小改动重写整份文本文件。结果通常一样，但除非文件很短或大半都要改，重写就是白花输出token和时间。

把这句追加到系统提示或第一条用户消息，它就回到前代在中小改动上的做法：

> For small changes to a file, edit only the relevant lines. Do not rewrite the entire file unless most of it needs to change.

重写出来的文件通常一模一样，差别只在账单和时间。

## 3. 另外7条逐条拆（含原文）

剩下7条同样有用，逐条展开。先说个分类：这7条里有3条是提示词，4条其实是配置或使用习惯——分清楚才知道劲往哪使。

**第1条 · 界面不显示（配置+提示词）**

问题：工具输出在界面上会被折叠或隐藏，模型不知道，会专门跑命令给你看界面根本显示不出来的东西。

官方给的是两步：先查客户端设置里进度更新（progress updates）有没有打开（默认 omitted 模式下模型写了你也看不见）；再检查提示词里有没有"所有发现留到最后再说"这类压制叙述的旧指令，有就删。

**第2条 · 该排版的时候就排版（提示词）**

旧的"少加粗、少列表"禁令该删了。官方原文：

> Use lists and bullet points when asked to, or when the content is multifaceted enough that they help with clarity.

中文：用户明确要求时，或内容层次够多、列表有助于理解时，才用列表和要点；对话场景保持纯文本。

**第3条 · 引用标注（提示词·示例式）**

总结文档时，5.1比前代更容易把原文成段搬过来却不标成引用。官方的做法不是给一句禁令，而是在系统提示里放一个完整正确示例：一份总结回复，附一段说明"为什么这个回复是对的"——让模型照着样子学转述，而不是照着禁令猜。

**第4条 · 压缩摘要（提示词）**

长对话压缩时，明确告诉它必须留住什么。官方给了六条保留清单：遇到的困难和解法、被排除的方案和原因、所有决策和约束（原话保留）、当前进度、待办事项、具体细节（名字、数字、日期、原文链接）。

其中最值钱的一句（中文意译）：用户说的话尽量保留原话，模型自己的推理可以大幅压缩——压缩完的新上下文里，你的原始意图还在。

**第5条 · 长输出别在草稿上耗光预算（配置）**

要长交付物时跑high档；真要跑xhigh/max，max_tokens得给思考和回复一起留量——5.1动笔前想得更久，预算只给回复会直接截断。

**第6条 · 对话历史只许追加（API硬约束）**

助手回复原样接上，别在两次请求之间改早先的轮次。8月31日后新建的账号强制执行：历史前缀一变，thinking块直接报400。正确姿势是把对话历史当 append-only 日志——不删、不改、不重写，新指令用中途系统消息追加。

**第7条 · 不用写提示词的五处（使用习惯）**

effort档位换模型后要重扫一轮（同名档位不同模型的思考量不等价）、安全误杀的三处高发场景、主agent别干等子agent启动、视觉任务给裁剪工具。这些改习惯就行，不用动提示词。

## 4. 我的实测：跑通一次两小时的无人值守

前两天我有个多步骤的长任务，但当时人腾不出手盯——AI中途的提问我一条都回不了。

搁以前的模型，这就是死局：它跑十几分钟，停下来问一句"要我继续吗"，没人应，就停在那。我回去戳一下，它再跑十几分钟，再停。一个晚上要戳好几次。

这次我只加了「自主推进」这一条，让它挂着自己跑。两个多小时，它把目标拆完、逐项执行，遇到真正需要人拍板的地方没有干等，而是记了备忘继续往下推进。第二天早上我打开一看，结果齐了，接上就能继续用。

整个过程没有出现一次"要我继续吗"。

几个感受：

第一，无人值守的前提是把"什么算破坏性操作"讲清楚。可逆的事让它大胆干，不可逆的事才留给人——这个边界要你自己划。

第二，这招不只对写代码有用。批量整理文件、批量调研、长文产出，凡是"交代清楚、结果可验收"的活，都适用。

第三，配合"小改动别重写整个文件"那条一起用，两个小时的账单也没有想象中吓人。

你被"要我继续吗"打断过几次？评论区聊聊。

## 5. 怎么用：三个落位

提示词落下去的地方不止一处，按生效范围选：

第一处，系统提示（如CLAUDE.md）：自主推进、小改动别重写、反文艺腔这类要长期生效的放这里，所有项目全局生效。

第二处，AGENTS.md的规则区：把授权边界写成明文规则，比如"可逆操作直接执行，不可逆操作先停下确认"。规则比对话提示词硬——AI每次都会读到，团队里其他人拿来也能直接用。

第三处，封装成skill：把验证过的模式打包成自定义skill或指令模板，需要的会话自动带上，不用每次手抄。

按需临时加的（进度叙述、压缩摘要这类），放每次对话开头一句就够。

我的建议：自主推进、小改动别重写、交付范围这三条先进系统提示长期生效；跑顺了，再把边界类规则固化进AGENTS.md，最后沉淀成skill——这就是把一条提示词变成自己工程体系的三步。

注意：8月31日后新建的账号，对话历史只许追加，别在两次请求之间改早先的轮次，前缀一变thinking块就报400。

## 6. 比提示词更重要的：这套思想怎么搬到你自己的工具栈

先说清楚：这12条不是「Fable 5.1专属咒语」。我自己主力也不靠它干活——这次也只把「自主推进」这一条真正抄进了自己的工作流实测，一条就值回票价，其余的按需取用。拆开看，这12条其实在说三件工程事：

给AI划授权边界——自主推进、交付范围，什么它能自己干完，什么必须停下来问人。

定通信协议——进度叙述、压缩摘要，过程怎么汇报、结果怎么留档、压缩时什么必须原样保留。

控成本——effort档位、小改动别重写，把算力花在真正需要推理的地方。

这三件事跟你用什么模型无关。它们和我一直在用的一类东西是同一个思想：我最早从Kiro自带的原生spec机制学到这套方法，后来演进成自己的规格说明书（SDD）驱动工作流——业内OpenSpec、Spec Kit走的也是同一条路：把「说清楚需求」变成工程件，意图、证据、规格各自落位，再交给AI执行。

所以这篇的正确用法不是「抄完提示词就关掉」。提示词只是这套思想的最后一公里——今天你可以先把自主推进抄走用起来；有空的时候，把「授权边界、通信协议、成本控制」这三层按上一节说的三个落位搬进自己的工作流：先系统提示，再AGENTS.md规则，最后skill。后者才是这篇真正想给你的。

## 写在最后

提示词不是写一次就永远管用的东西。模型升级了，脾气变了，提示词也得跟着调。

**Fable 5.1这12条官方模式，说白了就是一句话：别再用旧习惯伺候新模型。**

老提示词不用全删，该补的补、该删的删。官方指南值得通读，但如果你只有十分钟，就先抄两条：自主推进、小改动别重写。这两条解决的恰恰是最常见的两类浪费——干等，和重复输出。

其中自主推进这条，建议今天就加上——它会让AI从"需要你盯着的工具"，变成"能自己把活干完的同事"。我那两个小时的无人值守，就是它给的。

> 技术细节终会过时，工程思想历久弥新；模型会变、工具会变，但"顺着模型的脾气干活"这件事永远不变。
