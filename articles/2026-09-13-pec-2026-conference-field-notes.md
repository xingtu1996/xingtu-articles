> 一句话总结：2026 年 9 月 12 日，我去北京中关村参加 PEC 2026 AI 创新者大会，从上午坐到下午五点。上午四场圆桌，下午八场分享，中午还有三项年度发布。台上讲 Token 工厂、FDE、AI 出海、Harness。我发现自己过去一年在工作台里默默搭的东西，台上前辈们正在用更体系化的方式讲出来。

先说结论。这一天最值的不是哪个新概念，是四件事被盖章了。FDE 从一个我自己带回来的词，变成行业报告里的正式范式；Harness 从一个小圈子的黑话，变成工程师的基本动作；AI 的能力边界被画到了明面上——能不能写下来，就是那条线；我自己走的路，方向没偏。

下面按时间线写，从上午第一场圆桌说起。

## 开场那场圆桌，先给了两句话

大会第一场《2027，我们需要怎样的模型？》。椅子还没坐热，主持人第一个问题就问得很大。

台上几位老师里，有信通院人工智能研究所的所长，有面壁智能的多模态首席科学家，有清智资本的合伙人，还有一位清华的助理教授、同时是元环智能的创始人。四个人背景差得很远，但聊到"模型接下来往哪走"的时候，出现了一个高度一致的口径：通用的那个模型，会开始设计垂类的模型。

大屏上打出来的是「通用模型能够设计垂类模型，形成更高层次的统一」。我盯着这句看了半天——这句话的意思是，模型在给自己造下一代。不是人去调它，是它去生产它。

紧接着还有一句更狠的：「大公司组织体系庞大，转向较慢，总想把自身能力融入模型。」

这句我在台下想了很久。我平时说的 AI First，是手上这一层的事：有什么需要，先让 AI 出几版，人再判断取舍、调整润色。真正难的是上面那层：公司越大，越想把自身能力融进模型，可组织转向就是慢。手上这件事，一个人就能改；组织那件事，不是。

那这一步值钱在哪？我的判断：AI 出的几版里，最炫的那版往往不是能用的那版。炫技不是让人看不懂，是让人看得懂、有共鸣，还能看出你手上有活。这是我这一年在实践里慢慢得出的理解。

后面还有一个词，是我一整天都在想的：「我们启动了企业级语义层和本体建模工作，得到很多支持。」

还有两句话：

「牛顿力学虽能写出方程，边界和初始条件却无法符号化记录。」

「物理世界还有内容未被符号化，我们在做 AI for AI。」

这两句我先按住，后面专门讲。

## Token 工厂那场：真功力不在模型

上午第二场是《构建 Token 工厂》。这场我本来是抱着听热闹的心态去的——"Token 工厂"这个词我在会前刷到过好几次，总觉得像是个口号。

结果这一场反而是最"工程"的。

几位老师从推理性能讲到缓存层，再讲到出海。大屏上打出来的是「我们用 KV Cache 和提示词加速提升推理性能」「我们既产生更多 Token，也利用缓存层能力提升客户使用体验和效果」，还有一句「出海是未来的重要方向，服务 SLA 对客户使用很重要」。

翻译成人话：Token 工厂的胜负手，不在谁的卡多，在谁的工程做得细——缓存怎么用、延迟怎么压、SLA 怎么承诺。全是工程思想，不是模型能力。

后来中午发布的《Token 工厂全流程架构图》里，它被画成了一条流水线：

数据进（生产经营、客户交互、业务系统、物联网、外部数据）→ 算力车间（训练集群、推理集群，加一个专门的运营管理中心管能耗、稳定、调度、安全）→ 服务出（算力服务、Token 服务、场景赋能）。

最值得注意的是那个"运营管理中心"。它一克算力都不产出，但它管能耗、管稳定、管调度、管安全——**模型是生产线，保障车间才是工程能力。**

## 本地 AI 那场：评价标准换了

上午第三场聊的是"让模型更好跑在本地"，台上坐着 AMD、英特尔系、浪潮、戴尔、MiniMax 的人。这场的变化，一句话就能说清：

大屏上先写「过去我们更强调本地模型的 Token 速度和 TTFB（首字延迟）」，然后写「关注点已从 Token 数量转向本地模型能否完成任务」。

这两句放在一起看，是一次评价标准的换代。以前比谁跑得快，现在比谁干成事。快是性能指标，成事是结果指标。

台上还有一句我觉得可以贴在公司会议室里：「进入智能体 AI 时代，应将 AI 负载放在最合适的位置。」

不是全上云，也不是全本地，是按任务和数据敏感度精细路由。我自己归纳了一张三层表：公开信息走云端，一般业务数据走本地，敏感数据、自有 IP 走端侧或自建中心。

同场还有两个技术细节挺实在：DeepSeek V4 用了 FP4 与 FP6 混合精度；还有"用 SSD 分层换显存成本"——热数据放显存、冷数据换进 SSD，硬件配置不用堆到顶。这些都不是理论，是省钱省出来的经验。

## FDE 那场：这个岗位的边界被画出来了

上午第四场是《AI 转型：FDE 边界与第一推动力》。这场对我个人最要紧——因为我自己对外就是这个身份。

这场台上六位老师，大屏上的金句密度也最高，一口气 13 条。我挑几条最扎我的：

「部署大模型只是业务第一步，后面还有大量工作。」

这句话听着平淡，但它是全场最"反营销"的一句。所有人都在讲部署多快多省，只有它提醒你：部署只是第一天。

「FDE 需翻译并解耦业务需求，设计落地架构。」

翻译是往上，把业务的黑话翻译成技术语言；解耦是往下，把纠缠的系统拆开。FDE 是业务和系统之间的那个编译器。

「FDE 要应对复杂的企业运转和各家差异化的 ERP、CRM 流程。」

我在下面批了一句：FDE 的主战场是业务场景，不是编码场景——编码有确定性、能自动化；业务流程千奇百怪，只能人进去。

还有一句，是这天我最认同的之一：

「成本越来越低，审美、认知和知识就变得无比重要。」

这句是说给普通人听的，也是我这一天听到最定心的一句。当算力像水电一样便宜，值钱的东西就换人了——不是谁记得多、算得快，是谁看得准。

## AI 原生那场：怎么活、做什么、怎么收钱

上午最后一场是《Coding 之后的产品机会》。Coding 这个题，做技术的人都有话说。

这场三条金句，刚好是创业的三件事：

「产品要走开源和商业化并行的道路。」——怎么活。
「二次元内容特别适合用 AI 实现，我也是二次元迷。」——做什么。（我更在意的是后面那条线：内容生产的成本正在趋零）
「支付环节要提供适配地区和计费模式的支付方式。」——怎么收钱。

最后一条是 Stripe 的人讲的。翻译一下：计费模式就是商业模式的翻译器——你按量、按订阅、还是一次买断，决定了客户怎么理解你在卖什么。

## 下午开场：从买软件变成买 token

下午一点五十一，FDE 实战营开场。主持的是紫光智算的王培农老师。

他上来第一件事，是把"FDE"这个词的年纪翻出来了——2020 年 Palantir 的上市文件里就有。也就是说这不是什么新造的概念，是被人重新看见的老岗位。

然后他讲了付费方式的变化：

「从原先的软件范式变成了一个 token 的做法——以前买软件，今天买 token。我更愿意为 token 的结果付费。」

下面这句是他的暴论：30 年以后，每家公司都会拥有自己的模型——就像 2000 年做网站，现在谁都能搞。

他还补了一句我很认同的：私有化不是因为技术，是因为数据主权。"数据如果被蒸馏走了，我就没有价值。"

我写东西也一直在讲同一件事：**模型会换，工具会换，业务知识、规则边界、质量责任不会换。**今天台上有人替我说了。

## 郭美青老师的六层

第二场是百川智能的郭美青老师，讲医疗 Agent 的落地实践。

他给了一个六层架构，从下往上：

任务约束层（你的任务、你的约束是什么）→ 认知层（给它什么知识库、上下文、记忆）→ 决策层 → 行动层（配什么工具、怎么优化）→ 交互表达层（什么时候触发、怎么输出）→ 进化评估层（调优手段今天有效明天失效，所以必须能自己定义）。

我一开始以为六层里总有一层是"让模型更聪明"。听下来发现一层都没有——六层全是"让模型更可控"。

同场还有一组数据：同一个模型，换一套 Harness，效果差了 21.8 个百分点；任务从简单变复杂，达成度从 84.9 掉到 37.7。

同样是模型，差别全在外面那层。记住这个数，后面有用。

## 让我坐直了的那场

下午两点三十五，词元映射（tokenmap）的 CTO 梁凯锐老师上台。他没讲概念，从两行代码开始写。

他要回答的问题是：Agent 到底是个什么东西？

起点是 2022 年。那时候 ChatGPT 网页版只能聊天，不能干活。同一个时间，普林斯顿的 ReAct 论文把"观察—思考—行动"带进了大家的视野。

他先从两行代码开始：把用户输入拼进上下文，直接给模型。结果当然是——你让它查日程，它查询不了，因为它没有工具。

然后加了三行：把工具协议和工具集塞进上下文，模型要调用工具就承接、执行、再把结果写回上下文二次推理。他专门强调了一句，这五行代码的心脏是"把工具结果写回上下文"——不写回去，模型下一轮就不知道刚才发生了什么。

接着是死结。

查日期 → 查日程 → 订机票 → 订酒店 → 打车。这种链式任务，每加一个工具就得加一段代码。工具上百个，代码就无穷无尽。

他的做法很朴素：发现每次处理工具请求的代码高度相似，就把它提取出来，加一个 while 循环。

然后他说了那句话，我当场坐直了：

"执行工具没有变化、任务难度没有变化，只是加了一个循环——但决策权从程序手里，挪到了模型手里。"

我这么在意是有原因的。因为我自己工作台里那套东西，核心就是这个逻辑：根目录一份 AGENTS.md 当 AI 的入口指引，下面规则、工作流、技能、工具、spec 分层放，每个技能一份说明文件加可执行脚本，加起来七百多行规则、七十个 Skill。梁凯锐把这件事讲成了另外两个名字：`search_skill` 负责轻量目录，`load_skill` 负责按需加载。

后面还有一层优化，我觉得更聪明：几十个技能还好，企业里成百上千个技能，协议全塞进上下文光占位就受不了。所以把协议移出上下文，只留一个 search_skill 的入口，等于几百个技能只花一个入口的 token。

这场最后有个比方：对话是点，工具调用和上下文是线，Agent 是一个圈——模型自己决定什么时候用工具、什么时候停下来。

我在自己文章里用过类似的说法，但没他这么干净。

## 马石老师的散热片

下午三点零二，同场的马石老师讲了一个案例，是我这一天听到最不起眼、也最实在的一个。

有家做散热片设计和制造的公司，服务器散热需求爆发，生意很好。CEO 找到他，说的话很典型："我想用 AI 提升内部效率，但我不知道怎么做。"

他自己说，他的做法"比较粗暴"——不聊技术，先问几句："你给我看一下你的产品都在干嘛？你的销售在干嘛？是不是天天在骂你？你的制造是不是天天在等你？"

最后他没做中台，也没买一堆盒子，直接进核心流程。

这段里有两句话我认为是全场最有价值的：

第一句："这个流程绝对不是来自 FDE，也绝不是来自大模型——大模型能画出很多流程，但只有这个流程符合他们公司的实际情况，只能来自他们工程团队最有能力、交付最靠谱的那个人。"

第二句是关于"谁做谁不做"，他分得很清楚：三维理解和操作模型做不了，它没有 3D 知识，这块别指望它；**跟客户交互的地方最好别让代理去做——发错了，或者被识别出是 AI，会摧毁客户信任**；反倒是资料收集、启动仿真这些最耗时的环节，交给 AI 最好，因为一个仿真没跑好，后面所有东西都得重做。

他还说了一个我没想到的角度：这其实是个管理流程变更的问题，不是写代码的问题。以前一个人做整条线，输出质量取决于这个人的能力和责任心；现在是人和智能体分成了若干道工序，像 OA 审批流一样，没有 A 就不能到 B。

## 王书元老师的零售五阶段

下午三点十八，Google Cloud 大中华区 FDE 团队负责人王书元老师上台。他的 PPT 第一页写着两句话：

> 深入一线扎实填坑，连接业务长效修路。

第二句是：成功的 GenAI 落地不仅是模型的胜利，更是工程确定性与业务 Know-how 的深度协同。

他讲了一个零售 App 的完整流程，五个阶段，每个阶段都有硬东西：

准入——三个问题：用户意愿度够不够、技术难度有多高、体量值不值得。而且不是一个人拍板，是 FDE 经理、业务代表、架构师三方研判。他强调"拒绝过度承诺"。

需求诊断——第一件事不是画原型，是去看数据在哪，而且要调真实的样例数据出来看。用户旅程四步：打字 → 产品卡片 → 购物车 → 优惠券。成功指标是 DAU、客单价、点击率、下单转化率。

架构设计——FDE 当技术负责人，拉上产品和架构组成铁三角；核心架构、排期、commit、RACI 责任划分一次说清。

实施交付——他有个词叫 Path to Production，每一个节点都要客户领导背书；出了问题处置三连是：判差距 → 沟通破例 → FDE 兜底。

上线之后到二期——承接、培训、FDE 撤出机制；然后决定是做深（集团复制）还是做广（多用户推广）。

他还讲了 FDE 团队自己的三阶段演进：起步期需求远大于承接能力，所以设了严格的准入机制，专挑核心项目、专挑模型能力最不确定的地方；成长期人数和质量同步扩张；到 2027 年，成熟期的标志是业务代表和架构师主动把项目带进来。

以及一句我太熟的话：选哪个部门先做，没有通用规律，完全看人。工程师文化厚的地方推得动，老师傅抵触外化经验的地方，再好的方法也推不动。

我在公司几个项目组之间推统一的 AI 工程化规范，就是这个问题——每个人手里的 harness 体系都不一样，工具链不统一，连提示词风格都各写各的。后来专门做了一套标准规约包往下发，才慢慢对齐。

## 云舒的 Skill 账本

下午三点四十三，云舒老师讲《从 Skill 迭代到 Agent 开发》。他是公众号和即刻博主，个人开发者。

他讲自己走过的六段路，听着像笑话，其实每一段都是坑：

最早用 PRD 提示词；然后变成两个窗口来回倒腾；然后开始疯狂加 Skill——去年十月一口气做了四五十个；然后是 Skill 打架；然后做 dev-workflow 插件；最后是 Nexus 中台。

Skill 打架是什么样？他举了个例子：四十个 Skill 全预加载进上下文，你说"随便生成一张图"，设计图的 Skill 就被触发了。用户要的是自由，工具硬把你拉进固定流程。

他的解法有两条，本质都是减少上下文注入量：一是关掉不用的、把名字和描述写详细；二是把项目里十几个 Skill 打包成一个大的工作流插件，最后 Skill 数量压到 15 到 20 个。

他说了一句我一直记着的话：

> 60 分的 Skill 很好弄，想让 Skill 好用很难。我们内部改了 100 多版，也就七八十分。

外面那些教程教你写个 SKILL.md，三步搞定。真在生产环境跑过就知道，60 分到 80 分之间差的不是写作技巧，是跟真实用户反复磨。他还提了一个数：他们一个 PM，一天烧 1000 美元的 token。token 已经不是技术参数了，是工作量的新单位。

他还分享了一个失败案例：用户要"把页面结构完整重做"，AI 悄悄理解成"只复用视觉语言、不改结构"，然后实现和测试都照着这个错规格跑，居然全绿。他的处理是把这类错误归档成编号案例，下次先查。

以及三条我觉得可以直接抄的原则：

"把能交的交出去，人留三个关口——需求讨论、必要决定、最后验收。"

执行和检查要分开：让不同模型互相审，"同一个模型的 Subagent 盲点相似"；收到意见要逐条核实——成立的改，理解偏差的说明理由。

"我要的不是 Memory，是一个知识库。" 他这一年就在干这件事：从试点到生产，升格成集团级重点项目，现在实际开放 1800 人，规划是 10 万。

同一场我第一次听到 Spec Coding——PRD、测试用例、代码用同一套规格串起来，dev-workflow 自动从 PRD 生成测试用例、再生成代码，绿灯跑通就算交付。这让我意识到：原来"写代码"正在从"人写代码"变成"人写规格，代码自己写自己"。

## 央企那场血泪复盘

下午四点零二，是一场央企 RAG 项目的复盘，讲的是函子科技创始人蒋耀锴。一开口就知道是干过活的乙方：10 万人级集团，项目从普通项目升成了集团 A 级。

这场的信息量是全天最大的。按顺序说：

技术路线被客户种草——客户刷短视频看到一个新方案（不用切分、不用向量化，直接让大模型读一遍原文写目录当索引），让他们试试。他们试了，效果确实好一些——但一份文档入库要 50 分钟。"性感是有代价的，你得让它验证。"最后还是回到传统向量检索。

数字不好看但必须说：64.3% 对比 58.1%，只高 6.2 个百分点，但平均回答长度是对照组的 2.78 倍——准确率不是唯一指标。另一组是 0.20 到 0.72，调优三倍仍然有明显差距。

雨露均沾——一个人上传大量文件，不能堵住所有人的队列。"你的队列是你的队列，你来了先解析一份，别人来了也解析一份，每个人都在动。"他说公平调度从架构选项变成了生产必需。

质量已经不是"功能可用"，是"生产可信"——他们拿出的证据链是四组数字：39 项人工 Story Case 走业务关键路径，593 项 AI 辅助测试，900 多条真实问答持续进评测集，145 项 UI 走查整改。

他们甚至做了一个资源计算器：用户数量、存储空间、排队额度一变，自动算要几个 Pod、几张 GPU、每样东西多少钱。"不拍脑门。"

成本的大头不在开发——客户是建筑设计出身，对边距和间距苛刻到像素；领导用折叠屏，两天要适配完。他说了句我记到现在的话：**"核心的成本不在开发成本，在沟通成本，在信任成本。"**

天级迭代不是加班神话——"上午收到优化点，第二天就给新版本"——大模型压缩了需求澄清、开发、联调、回归的整个周期，加上视觉设计师现在能独立完成视觉优化任务。

还有一个细节我到现在还记得：网站挂了的时候，他们做了个卡通形象，给足用户情绪价值——"用户感觉网站没挂，至少还有 UI"。

以及最后一句，乙方听了会沉默：客户 IT 负责人多次邀请他和同事入职，他说这是信任升级的侧面证明。信任的三段升级是：真实试用 → 天级响应 → 邀请入职。

## 李锦威老师的 Design as Code

下午四点半，OpenDesign 的李锦威老师讲设计。

他先讲了一个变化：去年团队里还有设计师用 Figma，今年基本都用代码、用原型直接做交付。一个 PM 一天烧的 token 甚至高过开发。

他给了两句我很喜欢的话：

一句是「模型第一次真正有了审美」。另一句是「审美平民化」——世界级审美不再锁在少数人手里。

他解释为什么这事儿在以前做不到：传统生图式工具是 prompt 生图 → 图转 HTML → 再转生产代码，每一步都在失真。Design as Code 的意思是用代码本身做设计，产物天然可交付，中间那几段损耗全没了。

他给的数字也硬：开源模型在设计场景比肩顶级 SOTA，成本只要原来的百分之一（$0.023 对比 $1.61 一个任务）；换一套 Harness，效果直接上一档。他们还自建了一个评测集叫 Arena，把效果、成本、速度三个维度持续跑分，榜单公开可核。

然后是"评论即指令"：设计师在图上圈选，发到聊天里，Agent 逐条改，确认定稿。一周的定稿压到几小时，人只做圈选和确认。

最后是全天的尾声，OpenDesign 团队分享开源运营：完全开源加官方订阅，全球 400 多位贡献者，PR 三小时内判断并合入，一天近 100 个 PR。

支撑这一套的是一套 7×24 全自动的 PR 运营体系，五个环节：写（Coding Agent 拆任务生成补丁）→ 审（Bot 做安全、质量、风格审查）→ 验（自动化测试加视觉验证）→ 合入（Merge Gate 加人审，高危守底线）→ 沉淀（反馈变成资产）。

自动化程度越深，人守的那道底线反而越要显式。

## 我随口说的一句，和下午的答案

回到下午开场那一刻。王培农老师讲模型主权的时候，我跟旁边的人说了句："我觉得 Harness 价值变弱了。"

接下来一整个下午，台上各位老师几乎都在讲 Harness 有多重要——同一个模型换套 Harness 差 21.8 个百分点，换个 Harness 成本降到百分之一。数据和我的直觉正好相反。

我到现在还没完全想清楚这个问题。Harness 解决的是"模型还不够强、不够稳、不够听话"的问题，这个问题在今天成立，所以今天它值钱。可模型每三个月跳一级，那些外挂的提示词约束、工具路由、权限护栏，有多少会被模型自己内化？就像十年前写网站要自己管线程池，现在框架帮你管了。

## 模型学不会"盐少许"

回到上午那两句话。

就是牛顿力学那句，和「物理世界还有内容未被符号化」那句。

"符号化"这个词听着吓人，其实就是一句大白话：**能不能写下来。**

能写下来的，AI 全包；写不下来的，还得靠人。

你妈给你写过菜谱吧？"盐少许，油七成热。"六个字你都认识，照着做还是难吃。因为"少许"到底是多少、"七成"到底是多热，她说不太清，你学不太会——只能站灶台边上看她炒三年。

这就是写不下来的知识。AI 的边界，就画在这儿。

有意思的是，连牛顿力学都有它的"盐少许"。方程写得漂漂亮亮，边界条件和初始条件却写不出来——人类最硬的那套公式，也留着说不清的地方。

【配图：11_符号化光谱-未符号化地带是FDE主战场.png】

所以那个悬念，我现在有了一半答案：哪些东西会被模型自己学会？**能被写清楚的，它迟早学会；写不清楚的，挂再多工具也只是权宜。**

上午还有人提到，他们启动了企业级语义层和本体建模工作。我理解本体建模就是"把说不清的变成说得清的"那门手艺：概念、属性、关系、规则四条腿撑起来，一个场景才算被写进模型能读的地方。这大概也是 FDE 真正在施工的部分。

台下我还多想了一层，说出来供各位拍砖。

管软件和管 AI，其实是两件事。传统软件像个开关——按下去灯就亮，逻辑你能一条条列全。

模型不是开关。它更像一只特别能干、但主意特别大的狗。你没法跟它讲道理，也没法用开关控制它，只能一边牵着绳、一边圈个院子、再配上口令和零食，让它大体上往你要的方向走。

绳子、院子、口令、零食，加起来就是 Harness。

我现在觉得，"Harness 就是模型控制"这句话，用狗讲比用架构图讲清楚多了：**低维的东西才用开关，高维的东西只能这么哄。**

## 我押什么

一天听完，我只说三个押注，半年后回来对。

第一，模型还会继续便宜、继续通用。那张 Artificial Analysis 指数上，第一名和第十二名差 15 分；国内 API 最便宜的 DeepSeek V4 Flash，百万输入 token 只要 ¥0.1。我用什么模型的权重会持续下降，我在模型外面搭了什么才重要。我工作区里那七百多行规则、七十个 Skill，才是换模型时不用搬家的东西。就连这篇文章，也是按一套标准发布包流程走的——标题、正文、封面、配图、合集、推广文案、每一版的修改原因，各占一个目录，改了九版每一版都留痕。这套东西本身就是我自己的 Harness。

第二，FDE 会在一两年内分化成三条路：大厂建制、OPC 个体、传统 ISV 转型。我选的是 OPC 这条，但前提是你得把现场那些东西攒下来、下次能直接拿出来用；不然 FDE 就是一个高级外包。

第三，Harness 今年会从小众术语变成面试必考。"你怎么管你的 Agent"会和"你怎么写你的代码"一样，成为默认要看的东西。现在开始攒成本最低。

## 写在最后

我去之前有一点怀疑。一个人做内容、做工具、做工作台，时间长了容易自循环——你写的东西你自己信，你用的工具你自己顺手，但市场到底认不认？

今天给我的答案是：市场在认，只是换了个名字。

我叫它工作台，报告叫它 Harness；我叫它 FDE，报告叫它工程落地范式；我把工作流写成 Skill，报告把这件事列成了 Agent 的标准结构；我上午在台下想的"把说不清的变成说得清的"，台上报告管它叫本体建模和语义层。

技术细节终会过时，工程思想历久弥新。这句话我自己写过，今天在台上又听见了一次。不是从我自己嘴里。

- 哪些 Harness 会被模型学会，哪些不会？我的答案只有一句：能不能写下来。
