# FDE 能力模型：8 个维度拆解，从技术到沟通的完整画像

> 一句话摘要：FDE 不是"会用 AI 的全栈工程师"，而是项目管理、全栈架构、基础设施、AI 编排、领域建模、团队协调、沟通管理、文档能力八个维度的综合体。这篇把每个维度拆开讲清楚——定义、为什么重要、真实场景、怎么修炼。

【配图：01-能力模型全景图.png】

我做 FDE 项目之前，以为这就是个"什么都懂一点"的全栈岗位。直到在客户现场被环境问题、需求变更、团队冲突轮番教做人，才意识到 FDE 的能力模型远不是"广度"两个字能概括的。

FDE 的能力模型有 8 个维度，技术 4 条、软技能 4 条，每一条都有交付线——这也是 FDE 岗位一年涨 729%，真正能上手的人却不多的原因。

先说我是谁：一线做 FDE 交付的，文里每个判断都有项目账本背书。这篇写给三种人——想转 FDE 的拿它自查短板，要招 FDE 的拿它当面试框架，还在犹豫要不要上 FDE 项目的拿它判断配不配动用这个重手段。带走的是一张清单，不是一个概念。

## 1. FDE 不是万金油：每个维度都有交付线

FDE 常被误解为"万金油"，但能力模型把模糊的"复合型人才"拆解为 8 个可衡量的维度，让自查、招人、成长都有了参照物。

很多人听到 FDE 的第一反应是：这不就是什么都懂一点的全栈工程师吗？技术会一点、沟通会一点、项目管理会一点。这个理解大错特错。

"什么都懂一点"和"8 个维度都能独立交付"是两回事。前者是广度，后者是广度加每个维度的最低交付线。FDE 的每个维度都有明确的能力门槛——不是"了解"，是"能在客户现场独立搞定"。

我做过一个某快消巨头的企业级应用改造项目，小团队加 AI，一个多月交付了十多万行代码。这个项目里，8 个维度每一个都被真实考验过。项目管理上，从 4 个 Sprint 迭代调整为里程碑驱动，因为 POC 阶段迭代 overhead 大于收益；基础设施上，WAF 误拦截、CORS 跨域、容器部署问题，前前后后提了若干张 PaaS 工单；沟通管理上，甲方技术负责人临时提需求，前端同事直接回怼，我用三段话化解了冲突。

这些事没有一件是"写代码"，但每一件都决定项目能不能成。能力模型的价值就在这里——它把 FDE 从一个模糊的概念，变成了一张可以对照的清单。

为什么要求这么高？上周末 PEC 2026 的 FDE 实战营上，Google Cloud 大中华区 FDE 团队负责人王书元老师有一句话，我特别认同：FDE 团队是在最多千奇百怪的项目里摸爬滚打出来的，经验变化度最高，还要有面对用户沟通的能力。

【配图：11-扎实工程能力.webp】经验变化度这四个字，拆开看就是这 8 个维度——你在不同项目里被迫补的短板，最后拼成了这张能力清单。

当然，行业里对 FDE 的批评也没停过。企服老兵陈果 George 最近有篇传播很广的文章，观点很直接：FDE 在美国值得单独命名，是因为工程师长期驻客户现场在美国从来不是常态；而在中国，驻场定制是企业软件干了几十年的事，把美国因为 Palantir 特殊模式冒出来的现象拿到中国当新物种，会误导这个行业。评论区点赞最高的一条更扎心：不是 FDE 不好，是国内缺乏 FDE 的土壤——谁为探索和创新的过程付费？公司里没几个懂 AI 的人，"大多数是实施改个名字蹭热度"。

这些批评，对了一半。改了名的实施，确实不是 FDE。

【配图：02-真假FDE分界线.png】但判断真假的标准，不是看工程师坐在谁的办公室里，而是看交付物：过去驻场交付的是代码和人天，人走活就凉；真 FDE 交付的是客户接得住的能力——文档、Spec、SOP、一套客户团队自己能跑的方法。新瓶装旧酒也好，AI 时代本来就要回到那些跑通过的生产范式，再叠上 AI Native 的形态去重构组织和生产。工具会换，交付能力的骨架不会换。这两者之间的差距，就是这 8 个维度要量的事。

我的判断：FDE 不是广度，是每个维度都过了交付线的广度。

## 2. FDE 不是招牌，是最后一道选项

实战营上 Google Cloud 还讲了一个案例，我记得很牢。某零售客户想让他们派 FDE 过来改手机 App，做智能搜索和对话式下单。但 Google 自己在项目准入阶段先问了三个问题：用户意愿度够不够，这决定成单可能性；技术选型难度多大，这才轮到判断 FDE 必要性；用户体量撑不撑得起 ROI。三关过完，还要由 FDE 经理和解决方案架构师一起研判，才决定到底投不投。

【配图：03-准入三问答案.webp】

也就是说，连卖 FDE 的人自己都不是上来就推 FDE。上不上、值不值，要先算过账。FDE 不是招牌，是最后一道选项——问题复杂到必须有人扎进现场写代码了再上；问题本身都没想清楚，先回去把业务流程理明白比什么都强。

看懂这一点，再看能力模型就顺了：正因为它是最后才动用的重手段，投出去的每一个 FDE 都得能独立扛交付。这也是为什么我认为能力模型值得认真拆，而不是当成招聘 hot word 看看就算。

## 3. 项目管理：FDE 的方向盘

项目管理是 FDE 的方向盘。FDE 不是"拿需求写代码"，要管范围、管进度、管风险，在客户现场对最终交付负责。

项目管理是什么？对 FDE 来说，不是考个 PMP 证书挂在墙上，而是在客户现场能把范围、进度、风险三件事管住。范围管不住，需求蔓延到做不完；进度管不住，交付日期一拖再拖；风险管不住，一个环境问题就能让整个项目停摆。

为什么重要？FDE 驻在客户现场，客户的需求是模糊的、会变的。今天说要这个功能，明天看了 Demo 又想加那个。没有项目管理能力，FDE 就变成了"客户说什么就做什么"的执行者，最后交付不了还背锅。

真实场景。我在那个企业级应用改造项目里，原计划是 4 个 Sprint 迭代，每轮两周，共八周。但做到中期发现，POC 阶段单环境、小团队、甲方高频 Demo，Sprint 迭代的 overhead 大于收益——每个 Sprint 的规划会、回顾会、待办梳理，花掉的时间比实际开发还多。跟项目经理对齐后，果断取消 Sprint 拆分，改为里程碑驱动：M0 启动、M4 版本管理、M5 列表、M6 创建，每个里程碑完成后约甲方做阶段性评审。后来预算缩减，又从 9 个里程碑压缩到 4 个，范围收敛，提前两周交付。

顺带交个底，这是整个项目的真实时间框架：5 月底在 PRD 工作台把租户管理、资源配置这些 Epic 拆成编号 Story，6 月中旬进入日清日结——项目仓库里的 daily-summary 从 6 月 16 日到 7 月 3 日一天不落，7 月初收尾。所谓一个多月交付，不是修辞，是日历算出来的。

这个决策的核心是：项目管理不是生搬方法论，是根据项目阶段选对方法。

【配图：04-治理五节点.png】POC 阶段用里程碑驱动比 Scrum 高效，正式项目可能又需要 Scrum。FDE 要能判断。范围失控有多常见？那场实战营上专门有一场分享，题目就叫《拆解一个需求失控的"失败"FDE 项目》——失控到值得当成失败案例来讲，说明这是这个岗位的第一号坑。

"AI 都这么快了，还要流程干什么"是更常见的质疑。这个问题我专门做过一轮正反论证：把反方最强的论点逐条摆出来对，翻遍能查到的研究和案例，结论浓缩成一句话——形式可以随 AI 变，但启动、规划、执行、监控、收尾这些治理节点一个不能少，AI 改变的是每个节点的成本，不是治理的必要性。最有说服力的是 Palantir 自己的白皮书：FDE 这个岗位的首创者，标准化交付框架里 POC 中位数六到八周，交付的是生产级应用——快，靠的是压缩每个节点的耗时，不是跳过节点。有意思的是，喊"AI 时代不需要流程"喊得最响的几个案例，自己都在回补：Anthropic 官方发布了 SDLC Playbook，Karpathy 也亲口改了口，承认生产环境不设防真的会炸。

怎么修炼？三件事。第一，学 PMP 框架，但不要背术语，理解范围管理、进度管理、风险管理各自到底在管什么。第二，在自己的项目里练——哪怕是个人项目，也试着定里程碑、控范围、记风险。第三，复盘每个项目的延期原因，是范围没控住还是风险没预判，下次改进。

我的判断：项目管理不是按流程走，是在混乱中把事推到交付。

## 4. 全栈架构：FDE 的发动机

全栈架构是 FDE 的发动机。FDE 要能独立做前后端技术决策，不是"后端写不了找后端、前端写不了找前端"。

全栈架构是什么？对 FDE 来说，不是前后端代码都能写两行，而是能在客户现场独立做技术决策——这个功能用什么架构、数据库怎么设计、API 怎么定义、前端用什么组件库，都能自己拍板。

为什么重要？FDE 项目通常是小团队，甚至是一个人加 AI。你没有架构师可以问，没有技术委员会可以评审。客户系统大多是 Java 技术栈（Spring Boot + MyBatis + MySQL），前端是 React 或 Vue。如果你的主栈是 Node.js 或 Python，到了客户现场就得补课，补课周期不可控。

真实场景。那个企业级应用改造项目，后端一万多行 Java 代码、上百个 Java 文件，由我加 AI Agent 独立完成。前端一万行左右由前端同事主建，AI 参与联调。中间涉及多租户架构设计——DB-per-Tenant 模式、分库分表中间件、Market Pack 概念，这些都需要独立做架构决策。有一次前端同事问某个 API 的数据结构，我当场给出设计方案，不需要等架构师评审。如果我只能写后端不能理解前端，或者只能写前端不懂数据库设计，这个项目的沟通成本会翻倍。

怎么修炼？第一，主栈要深。Java 后端的 Spring Boot 自动配置原理、设计模式实际应用、慢 SQL 排查、Redis 三穿、消息队列可靠性，这些是基本功。第二，前端要能上手。React 或 Vue 选一个，能独立写完整页面，理解状态管理。第三，多做技术决策练习——看到一个功能，先想自己会怎么设计，再看别人的方案对比。

我的判断：全栈不是前后端都能写，是前后端都能拍板。

## 5. 基础设施：FDE 的维修工具箱

基础设施是 FDE 的维修工具箱。客户现场的环境问题不会等 SRE 来修，FDE 要能自己排查 VPN、CI/CD、WAF、APIM、K8s 的常见故障。

基础设施是什么？对 FDE 来说，不是要成为 SRE，而是在客户现场遇到环境问题时，能自己定位、自己提工单、自己推动解决。VPN 连不上、CI/CD 流水线挂了、WAF 误拦截了 API、APIM 路由配错了、K8s Pod 起不来——这些问题在客户现场每天都可能发生。

为什么重要？客户现场的基础设施通常是甲方统一管理的，你没有 root 权限，不能自己改配置。出了问题要提工单、跟甲方运维沟通、描述清楚现象和根因。如果你连"WAF 误拦截"和"代码 Bug"都分不清，工单提错方向，解决周期会拉长好几倍。

真实场景。那个项目里，前前后后提了若干张 PaaS 工单。有一张是 WAF 误拦截——API 请求返回 403，但代码逻辑没问题，查了半天发现是 WAF 规则把某个请求头当成了攻击特征。还有 CORS 跨域问题——前端调后端 API 被浏览器拦截，需要在 APIM 层配置跨域策略。容器部署问题——Pod 启动失败，查日志发现是 ConfigMap 挂载路径不对。这些问题每一个都能让开发停摆半天，但 FDE 要有能力快速定位是基础设施问题还是代码问题，然后精准提工单。

怎么修炼？第一，从 PaaS 工单开始练。WAF、APIM、CORS、K8s 问题是 FDE 的日常，不是 SRE 的专属。每次遇到环境问题，记录现象、排查过程、解决方案，沉淀成自己的排障手册。第二，理解常见基础设施组件的工作原理——不需要精通，但要知道它们是干什么的、出问题会有什么表现。第三，本地环境从零搭建一次，VPN、CI/CD、容器化，亲手踩过坑才记得住。

我的判断：基础设施排障能力不是加分项，是客户现场的生存技能。

## 6. AI 编排：FDE 的效率倍增器

AI 编排是 FDE 的效率倍增器。不是"会用 ChatGPT 写代码"，而是把 Prompt、规则体系、工作流 SOP、Agent 编排成一套可复用的工程化体系。

AI 编排是什么？对 FDE 来说，不是日常用 AI 工具写几行代码，而是把 AI 能力体系化——Prompt 工程保证输出质量，规则体系约束 AI 行为，工作流 SOP 标准化操作流程，Agent 编排让多个 AI 角色并行协作。这四件事合在一起，才叫 AI 编排。

为什么重要？AI 工具谁都能用，但用出十倍效率差的人不多。差别就在编排——你是每次重新写 Prompt，还是有一套规则体系让 AI 自动匹配工作流？你是一个人跟 AI 对话，还是编排了架构专家、代码审查员、前端专家多个 Agent 并行评审？编排能力决定了 AI 是玩具还是生产力。

真实场景。那个项目里，我搭建了一套 AI 工程化体系：多套规则文件（安全规则、术语规则、Java 规范、React 规范、数据库规范等），十余条工作流 SOP（需求调研、原型驱动、PRD 输出、设计决策、代码开发、一致性检查等），多个专家 Agent（架构专家、代码审查员、前端专家、多租户专家、产品专家等），还有数十条跨会话持久记忆。这套体系让 AI 不是"每次从零开始"，而是"意图识别→匹配工作流→按 Spec 实施→专家评审→质量门禁"的标准化流水线。

【配图：05-编排资产实数.png】一个多月交付十多万行代码，靠的不是 AI 多聪明，是编排得当。这些不是概念摆设，现在都能数出来：项目仓库的 .claude 目录下，12 个专家 Agent、12 条工作流、6 套规则文件，加上记忆、模板和 Spec，一共三百多个 Markdown 文件。

怎么修炼？第一，从写规则文件开始。给你的 AI 工具写一套项目规则——命名规范、架构约束、安全要求，让 AI 每次自动加载。第二，沉淀工作流。把重复的操作（需求分析、代码审查、文档生成）写成 SOP，下次拿来就用。第三，尝试多 Agent 协作。让一个 AI 写代码，另一个 AI 审查，第三个 AI 写测试，并行推进。第四，建立记忆系统。把项目知识、用户偏好、踩过的坑记录下来，让 AI 跨会话记住。

我的判断：AI 编排的核心不是 Prompt 写得多好，是把 AI 变成可复用的工程体系。

## 7. 领域建模：FDE 的翻译引擎

领域建模是 FDE 的翻译引擎。FDE 面对的每个客户都是陌生行业，要在几周内理解业务规则、建立领域模型、翻译为可落地的技术方案。

领域建模是什么？对 FDE 来说，是快速理解一个陌生业务域，把业务规则、实体关系、流程逻辑抽象成技术模型——数据库表怎么设计、领域对象怎么划分、业务规则怎么编码。这不是"需求分析"，需求分析是听客户说要什么，领域建模是理解客户为什么要、背后的业务逻辑是什么。

为什么重要？FDE 驻在客户现场，每个项目都是一个新行业。这次是快消巨头的资金管理，下次可能是海事集团的应用改造，再下次是零售企业的供应链系统。你不可能提前懂所有行业，但要有能力在几周内摸清楚业务规则。领域建模能力差的 FDE，做出来的系统表面上功能都有，但业务一用就发现逻辑不对——因为他只实现了"客户说的功能"，没理解"功能背后的业务规则"。

真实场景。那个快消巨头的项目，业务域是企业资金管理，涉及大量复杂业务概念——资金账户、支票簿、资金池、客户层级、市场绑定。这些概念每一个都有特定的业务规则和关联关系。我用 PRD 工作台 SOP 来解构：先从甲方资料中提炼功能清单，再拆成 Epic 和 Story，然后写角色用例（Given/When/Then 场景），再梳理主流程，最后画原型。这个五步流程就是领域建模的过程——从模糊的业务描述，逐步抽象为结构化的技术模型。最后设计出 5-Layer 架构，每一层对应一个业务抽象层级。

【配图：06-AI落地最大裂缝.png】这套流程留下的痕迹现在还在：PRD 工作台从功能清单、Epic 和 Story 拆分、角色用例、Backlog 到人天评估，五步五个目录，Epic 的编号一路追到每一条 Story，谁都能顺着编号查到当初为什么这么拆。

怎么修炼？第一，练结构化拆解。拿到任何陌生业务，先问三个问题：有哪些核心实体？实体之间什么关系？业务规则是什么？第二，用 PRD 工作台方法。功能清单→Epic/Story→角色用例→主流程→原型，五步走下来，业务模型自然就清晰了。第三，多读甲方资料。客户的知识库、操作手册、历史文档，是理解业务最快的途径。第四，画 ER 图。不管多简单的业务，试着画一张实体关系图，画不出来的地方就是你没理解的地方。

我的判断：领域建模不是听客户说要什么，是理解客户为什么要。

## 8. 团队协调：FDE 的黏合剂

团队协调是 FDE 的黏合剂。FDE 项目通常是分布式小团队，成员在不同城市、不同公司，FDE 要能分配任务、跟进反馈、处理冲突，让团队像一个人一样运转。

团队协调是什么？对 FDE 来说，不是当项目经理管一堆人，而是在小团队里把每个人的长处用起来、把信息对齐、把反馈跟到底。FDE 项目的团队通常很精简——后端、前端、测试，加起来几个人，而且可能分布在不同城市、不同公司，远程协作。

为什么重要？小团队的协调成本看起来低，但实际上更高。因为人少，每个人的角色边界模糊——后端要不要帮前端调 API？测试发现 Bug 是顺手改掉还是提给开发？这些问题没有明确流程，全靠协调。协调不好，前端等后端、测试等开发、信息不同步，内耗拖死进度。

真实场景。那个项目团队分布在四地：北京、广州某外企科技公司、广州某合作方、广州甲方。前端同事在广州，测试同事也在广州，我在北京，甲方在广州。所有沟通通过在线会议和即时消息进行。我的协调方式是：统一对接——前端和测试的工作安排、反馈、问题都通过我来中转，避免前端越过我去找测试、测试越过我去找前端，信息到处飞。任务分配上，根据每个人的专长——前端 90% 由前端同事独立完成，AI 辅助复杂组件；测试 80% 由测试同事执行，AI 生成单元测试；后端和文档 90% 由我加 AI 完成。反馈跟进上，前端发现 API 数据不够，告诉我，我调整设计后同步给前端；测试发现验收标准无法测试，我补充 PRD 后同步给测试。整个团队像一个人一样运转，没有信息孤岛。

【配图：07-FDE职责链.png】

怎么修炼？第一，练统一对接。小团队里不要让信息乱飞，设一个统一的信息入口和出口。第二，任务分配看人下菜碟。每个人的专长和短板不同，把任务分给最合适的人。第三，反馈要有始有终。收到反馈后 24 小时内给出处理方案，不要让反馈石沉大海。第四，记录决策。团队的每个技术决策、范围变更、优先级调整，都记录下来，避免反复讨论。

我的判断：团队协调不是管一堆人，是让几个人像一个人一样运转。

## 9. 沟通管理：FDE 的润滑剂

沟通管理是 FDE 的润滑剂。客户现场的沟通不是"能说话"就行，要能消除冲突、同步信息、翻译需求、高情商收尾，在人际关系张力中把事推下去。

沟通管理是什么？对 FDE 来说，不是性格外向、能说会道，而是在客户现场的复杂人际关系中，能把事办成。具体包括四件事：冲突消除——发现对话有摩擦风险时主动介入；信息同步——发现不同角色之间信息不对齐时主动对齐；需求翻译——把业务需求翻译成技术实现，把技术方案翻译成业务语言；高情商发言——拒绝需求但不拒绝人，接受裁决但不内耗。

为什么重要？FDE 驻在客户现场，每天面对的是甲方的 PO、项目经理、产品经理、技术负责人，还有自己团队的前端、测试。这些人各有各的立场、各有各的信息、各有各的压力。沟通管理不过关，一个需求冲突就能让项目停摆，一句说错的话就能让客户关系崩掉。

真实场景。项目中期，甲方一位技术负责人提出新需求，希望尽快看到 QA 版本。前端同事直接回应："现实情况是，这么还没开发，至少前端是。"——需求期望和现实出现 gap，对话有摩擦风险。我介入，三段话化解：

第一段，信息同步："信息有些 gap，我来同步分享一下。目前几个业务系统是两条线并行推进，工作节奏不完全一致，但信息和需求同步不应该断。"——先承认 gap，再解释原因，不让任何一方觉得被针对。

第二段，技术翻译："某老师提到的新需求我看了下，就是加个字段的事情。"——把需求文档翻译为技术实现描述，让所有人都理解工作量，也让甲方知道这个需求不复杂但当前排期做不了。

第三段，高情商收尾："没问题的，也感谢某老师同步分享信息。"——即使需求暂时做不了，也不让对方觉得被拒绝。最后甲方 PO 决策"先记录到 backlog"，我跟进"好嘞"——接受裁决、不争论，随后主动推进正事。

这个案例里，AI 帮不上任何忙。AI 不理解人际关系张力，不知道谁手里有什么信息，不会维护关系，不会察言观色把握时机。

【配图：08-人机分工边界.png】会上我还记下另一个判断：FDE 响应用户就是快——直接沟通没有消耗，信息零跳转。很多公司做不到天级响应，不是技术不行，是沟通链条上隔了太多层。

怎么修炼？第一，记录每次团队摩擦的化解过程，提炼成沟通剧本，下次遇到类似场景拿来就能用。第二，练"先同步再翻译最后收尾"的三段式沟通，遇到任何冲突都按这个结构来。第三，观察高情商的人怎么说话——他们怎么拒绝别人、怎么表达不同意见、怎么维护关系。第四，控制 ego。客户说 backlog 就 backlog，不要争论、不要内耗，接受裁决后推进正事。

我的判断：沟通管理的核心不是能说，是在人际关系张力中把事办成。

## 10. 文档能力：FDE 的记忆外挂

文档能力是 FDE 的记忆外挂。FDE 项目交付完，客户要能接得住、维护得了，全靠文档。PRD、设计文档、Spec、SOP、会议纪要，每一种都要能写。

文档能力是什么？对 FDE 来说，不是"会写 Word"，而是能根据不同场景写出不同类型的技术文档——PRD 讲需求和验收标准，设计文档讲架构和 API，Spec 讲具体功能的分析和实施清单，SOP 讲操作流程，会议纪要讲决策和待办。每种文档的受众、目的、格式都不同。

为什么重要？FDE 项目交付完，人就撤了。客户要自己维护系统、迭代功能、排查问题，全靠文档。文档写得好，客户接手顺畅，项目口碑好；文档写得差，客户接手困难，后续问题不断，项目等于白做。而且 FDE 自己也需要文档——项目中期换人、AI 跨会话协作、需求变更追溯，都靠文档。

「甲方能接手」这四个字有多重要？PEC 实战营有场分享，题目就叫《好的 FDE 交付：甲方能接手，FDE 从重复维护走向持续价值交付》——交付的终局判断标准，就是人撤了之后客户接不接得住。

真实场景。那个项目一个多月产出了七万多行文档，近三百个 Markdown 文件。包括 4 个 Epic、10 个 Story 的 PRD，十多个 Spec（每个 Spec 包含分析、需求、设计、任务四份文档），5 份架构设计文档，大量会议纪要和测试脚本。这些文档不是"写完就扔"，而是在项目中反复使用

【配图：09-价值阶梯.png】——前端同事看 PRD 理解需求，测试同事看验收标准写用例，甲方看设计文档评审方案，AI 看 Spec 生成代码。文档是整个项目的单一事实源。

怎么修炼？第一，每种文档类型都写一遍。PRD、设计文档、Spec、SOP、会议纪要，不要只写自己熟悉的类型。第二，用模板。每种文档建一个模板，下次往里填就行，结构不会缺。第三，写给读者看。PRD 写给产品和测试看，要用业务语言；设计文档写给开发看，要用技术语言；SOP 写给运维看，要步骤清晰。第四，文档要跟代码同步。改了代码就要改文档，不要让文档和实现脱节。

我的判断：文档不是交付的附属品，是交付本身。

## 11. 能力模型怎么用：自查、招人、成长路径

8 个维度的能力模型不是看完就完，要拿来用——自查短板、招人对标、规划成长。每个维度都有明确的修炼路径，不需要等"准备好了"再开始。

能力模型的第一个用途是自查。如果你正在考虑转 FDE，用这 8 个维度给自己打分——每个维度是"能独立交付""需要协助""完全不懂"哪一档？8 个维度里有几个"完全不懂"？硬门槛（项目管理、全栈架构、沟通管理）过了吗？答案会告诉你离 FDE 还有多远。

第二个用途是招人。如果你是技术管理者，要招 FDE 方向的人，用这 8 个维度做面试考察框架。不要只考技术深度——Java 问得再深，沟通管理不过关，到了客户现场也拿不到需求。也不要只看简历上的"全栈"标签——要验证每个维度是不是真的过了交付线。

最近看到 Kimi 的招聘标准，跟这个思路是一个方向：围绕一个想法迭代 100 次、品鉴过 1000 个产品或作品、在一个领域投入 10000 小时。

【配图：10-Kimi人才画像.png】三组数字考的都不是知识点，是迭代过的手感和长期投入的积累——这跟"每个维度都过了交付线"是同一种判断逻辑，考察的是交付线，不是简历线。

顺带祛个魅：别冲着"高薪"两个字入行。陈果那篇文章里有个数据点很实在——翻美国大厂 FDE 的招聘广告，薪酬其实就是一线软件工程师的平均水平，贵的是这种工作方式，不是岗位溢价。这个岗位真正的回报是过程：8 个维度被真实项目逐个逼着补齐，这样的人在哪里都值钱，不靠头衔。

第三个用途是成长路径。8 个维度不需要同时补齐，有优先级。先补硬门槛——项目管理、全栈架构、沟通管理，这三个不过关，其他维度再强也做不了 FDE。再补核心维度——基础设施、领域建模、团队协调、文档能力，这四个决定交付质量。最后补加分维度——AI 编排，这是效率倍增器，但可以在做项目的过程中逐步建立。

成长路径上有一个误区：很多人觉得要"准备好了"才能做 FDE。实际上，8 个维度没有任何人是全部满分的。FDE 是在做项目的过程中成长的——你接了一个 FDE 项目，发现基础设施排障不行，就去补；发现文档写得不好，就去练。边做边补，比"准备好了再开始"高效得多。

我自己就是这样。做那个企业级应用改造项目之前，我没有完整的 AI 编排体系，没有处理过那么多 PaaS 工单，没有写过那么多 PRD。但项目逼着我把 8 个维度都过了一遍，做完项目，能力模型就建起来了。

我的判断：FDE 不是准备好了才做，是做着做着就准备好了。

## 12. 核心结论

- FDE 能力模型有 8 个维度：项目管理、全栈架构、基础设施、AI 编排、领域建模、团队协调、沟通管理、文档能力，前四个偏技术，后四个偏软技能
- 每个维度都有明确的交付线——不是"了解"，是"能在客户现场独立搞定"，8 个维度没有短板的人极其稀缺
- 技术维度决定能不能干活，软技能维度决定能不能把事办成；沟通管理和领域建模是 AI 暂时替代不了的核心竞争力
- 能力模型有三个用途：自查短板、招人对标、规划成长；硬门槛（项目管理、全栈架构、沟通管理）优先补齐
- 真假 FDE 的判断标准是交付物：交付代码和人天的是驻场外包，交付"客户接得住"的能力才是 FDE；连 Google Cloud 投 FDE 都要先过准入三问，它不是招牌，是最后一道选项
- FDE 是在做项目的过程中成长的，不需要"准备好了"才开始，边做边补比空想高效得多
