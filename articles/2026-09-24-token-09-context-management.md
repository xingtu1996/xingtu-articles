# AI 越用越笨？问题不在模型，在上下文管理

【配图：00-封面引子图.png】

> 行途导读：我花 25 美元修一个 Bug，发现账单几乎全付给了被清空的缓存。AI 不是变笨了，是上下文没管好。这篇讲清楚 AI"变笨"的四个机制，和六招上下文管理的工程动作——最后是我的真实数据：800 多个 session、300 亿 token，缓存命中率 98%。

先说结论：AI 越用越笨，不是模型退化，是上下文管理失效。同一个问题，AI 不会记错，它只是每次都要重新读一遍你给它的所有历史——历史越长、越乱、越脏，它表现就越"笨"。省 token 的本质也不是省推理，是管好上下文。模型是"会变"的，上下文管理是"不变"的工程思想。

## 我花 25 美元修了一个 Bug

上周我让 Claude 修一个线上 Bug。修完了，账单 25 美元。

修一个 Bug 花 25 美元，贵得离谱。我翻账单，发现钱几乎全花在"重新读上下文"上了——我中途把模型从 Opus 4.8 切到另一个模型试了一下，再切回来，提示词缓存（Prompt Cache）被完全清空，之前缓存的几万 token 全部重新计费。

也就是说，Bug 本身不难，难的是我让 AI"重新认识这个项目"的成本。

这个教训值 25 美元：**模型切换的账单，一半是缓存清空的账单。**

## AI 不是变笨，是这四件事在作怪

你肯定遇到过：同一个问题，AI 改了三遍还错；对话长一点，它开始答非所问；上一条它说错了，下一条还在错的结论上继续。

这不是玄学，是四个机制：

第一个，它没有真正的记忆。AI 每次回答都要重新读一遍完整对话历史，理解上下文全靠这次重读。

第二个，上下文窗口有限。对话太长，AI 会把前面的内容压缩成摘要，细节在这一步就丢了——你三个月前提的需求，可能只剩一行字。

第三个，注意力分散。哪怕窗口够大，信息太多 AI 也顾不过来。中间位置的需求尤其容易被忽略，这叫 Lost in the middle。

第四个，上下文污染。之前哪一步答错了，错误记录还在对话里，AI 没法自动清除，反而拿它当"事实"继续推导。错上加错，就是这么来的。

这四个机制叠加，表现就是：AI 越用越"笨"。其实它没变，是你的上下文变脏了。

## 省 token 的本质是上下文管理

想明白这点，省 token 的答案就出来了。

省 token 不是把提示词写短点、少问两句——那是省推理。真正的杠杆在缓存：让 AI 每次重读时，大部分内容直接命中缓存，不用重新算。100 个 token 里 98 个命中缓存、只有 2 个重新计算，和 100 个全价重算，成本差 50 倍。

所以上下文管理，本质是**缓存管理**。下面六招，都是围绕它展开的。

## 六招上下文管理（每招都有真实场景）

**第一招：缓存断点——静态内容在前，动态内容在后。**

系统提示、工具定义、项目背景这些"不变"的内容放最前面，用户的提问放最后。这样每次请求的前缀不变，缓存才能命中。反过来，如果在提示词里塞了动态时间戳、临时 ID 这类易变变量，前缀哈希一变，整个缓存全废。

**第二招：推迟模型切换——换模型选在"必然重写缓存"的时刻。**

对话压缩、工具调用结果清理这类操作，本来就会强制刷新缓存。要切模型，就趁这种时刻切——反正缓存都要重写，切换不额外花钱。千万不要在普通对话回合里随手切模型，那等于主动把缓存清了再付全价。我那个 25 美元，就是这么交的学费。

**第三招：预热缓存——先发一个 max_tokens: 0 的请求。**

正式进入复杂业务前，先发一个不生成任何输出的请求，把提示词预写入缓存。等真正开始干活，第一次查询直接命中热缓存，首包延迟和成本一起降。

**第四招：单次任务原则——一窗一事，别混谈。**

在一个对话窗口里只专注一件事。同时讨论三个复杂任务，上下文互相污染，AI 越聊越糊涂。我现在的做法更彻底：大任务直接开多个 session 并行，每个 session 各管一摊，互不污染。这招在工程上的名字叫"子代理隔离上下文"。

**第五招：交接说明——换会话前，把关键状态写下来。**

反复纠正同一个错误，AI 还在同一个坑里打转？别在旧窗口里耗，果断开新会话。但开之前，先让 AI 把项目背景、已定的结论、还挂着的事，整理成一份"交接说明"，新会话从这份文件起步，而不是从零开始。

这招我天天用：跨会话接续靠交接包（spec 三件套 + 会话交接文件），Agent 换班、模型切换都靠它续上——接手的人不用重新认识项目，上下文从交接文件开始，接得住。和第六招配合着用：规则进 AGENTS.md，状态进交接文件。

**第六招：长期设定进文件——画像和规则写进 AGENTS.md，不让压缩机制吃掉。**

像个人画像、团队规则这种长期不变的内容，写进专门的文件（AGENTS.md / CLAUDE.md），AI 每次从文件读，而不是依赖对话里的口头交代。文件内容不会被压缩机制处理掉，也不会因为对话滚动而丢失。

## 我的真实数据：98% 的 token 都是缓存

说点我自己跑出来的数字，不是云评测。

我本地 Claude Code 通过 CC Switch 跑了 4 个多月：800 多个 session，累计 300 亿 token（输入 4.9 亿、输出 0.7 亿、缓存读取 298 亿），缓存命中率 98%——100 个 token 里 98 个是缓存直接给的，真正新算的只有 2%。总成本 337 美元。你想想，如果没有上下文管理，这 300 亿 token 全价重算，账单要翻几十倍。

这就是为什么我说省 token 的本质是上下文管理。模型切换、提示词精简、压缩工具，都是手段；让缓存命中率上去，才是目的。

【配图：04-真实数据卡.png】

今天干活的方式也验证了这套东西：我手上一个交付项目，21 页的客户功能规格文档要解析成五件交付物（中英对照、界面实证清单、差异分析、人天评估修订、QA 清单）。我的做法是开多个 session 并行——一个 session 管需求工作台，一个 session 管接口核实，各干各的；每个复杂任务先写 spec（requirements/design/tasks 三件套）再让 Agent 执行；琐碎的、可并行的事直接丢给子代理，不让它污染主线上下文。人天评估改了三版，每一版都在新 session 里做，旧版本归档——上下文干净，改起来才快。

顺便说一句，最近火的 Jev 也印证了这个方向。它是个判断型模型，不做长文本生成，只输出"分类、打分、布尔值"这类结构化判断，速度快 100 倍、输出 token 免费。省 token 的另一半，就是尽量把"生成"换成"判断"——生成费 token，判断几乎不费。

## 结论：先管上下文，再谈换模型

我押一个注：上下文管理，是 AI 工程师未来三年最值钱的基本功。

模型会一直换——今天 Opus，明天 Jev，后天不知道谁。但你管理上下文的方法不会过时：静态内容在前、缓存断点、单次任务、交接说明、子代理隔离、长期设定进文件。这些是"不变"的工程思想，跟具体模型无关。

技术细节终会过时，工程思想历久弥新。

你的 AI 越用越笨？别急着换模型。先看看它的工作台，是不是被你搞乱了。
