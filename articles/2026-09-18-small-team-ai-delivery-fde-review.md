## 1. 项目背景：一个多月，十多万行代码，怎么做到的


先交代项目背景。前段时间，我作为 FDE 主导了一个某快消巨头的企业级应用改造项目。客户要把一个老旧的业务系统重构为现代化的多租户管理平台，涉及后端服务、前端门户、配置管理三个子系统。

团队规模很小，核心成员就几个——我负责后端和架构，一位前端同事负责前端，一位测试同事负责测试，还有项目经理和架构师做前期支持。团队分布在四地，全部远程协作，沟通通过在线会议和即时消息进行。

时间很紧，从启动到交付只有一个多月。最终交付了什么？

【配图：03-交付规模数字卡.png】后端一万多行 Java 代码、上百个 Java 文件；前端一万行左右 TypeScript 代码；文档七万多行、近三百个 Markdown 文件；AI 工程化资产两万多行、上百个文件；还有大量测试脚本和会议纪要。加起来十多万行、数百个文件，多次迭代提交。

这个交付量在传统开发模式下，至少需要三到四倍的时间和人力。我们能在一个多月完成，AI 编程助手功不可没——但更重要的是，我们建立了一套让人加 AI 高效协作的工程化方法论。

这篇把这套方法论拆开讲。不是"AI 自动写代码"的玄学，是每一步都有具体做法、有验证标准、有踩坑记录的工程实践。

AI 是效率倍增器，但方向盘和刹车都在人手里。

## 2. 团队架构：FDE 统一对接，小团队远程协作

【配图：02-FDE团队三阶段演进.webp】


团队架构是这套方法论的起点。小团队最怕的不是人少，是信息乱——前端直接找测试、测试直接找甲方、甲方直接找前端，信息在不同角色之间传来传去，最后谁都不知道最新版本是什么。

我们的做法是 FDE 统一对接。我作为 FDE，是团队的信息枢纽——前端同事的工作安排、反馈、问题通过我来中转；测试同事的用例、Bug、验收反馈通过我来中转；甲方的需求、评审、决策通过我来中转。不是我要揽权，是小团队需要一个单一信息入口，避免信息孤岛和版本混乱。

具体分工上，后端 100% 由我加 AI 完成。前端 90% 由前端同事独立完成，AI 辅助复杂表单组件和 API 联调。测试 80% 由测试同事执行，AI 生成单元测试和质量扫描。文档（PRD、设计、Spec、测试）90% 由我加 AI 完成。

AI 在团队里是什么角色？不是"工具"，是"虚拟团队成员"。它有自己的"工作区"——一套规则文件、工作流 SOP、专家 Agent 定义、持久记忆。这套东西，行业里叫"技能包"（Skills）——把 AI 干一类活的完整能力打包：规则、流程、专家、记忆。

它不是散装的几行配置，是能整体复制、整体迁移、整体升级的能力单元。

国家层面讲"人工智能+"，落到团队身上就是技能包——把老师傅脑子里怎么干活的那套东西，变成 AI 能照着执行的标准件。

谁沉淀的技能包越多，谁复用 AI 的效率越高。

它能独立完成代码生成、文档撰写、Spec 输出、代码审查、质量扫描、工作流编排。但它的所有产出都要经过人的审核——FDE 是 AI 的"项目经理"，定方向、审产出、把质量关。

远程协作怎么保证效率？三个做法。第一，所有决策留痕——技术决策、范围变更、优先级调整，都记录在文档里，不靠口头传达。第二，周频 Demo——每周给甲方做一次演示，反馈即时同步到 Spec 文档，下周 Demo 验收。第三，问题结构化归档——每个生产问题或技术难题，都记录"现象、分析、修复"三件套，可检索、可复用。

小团队的核心不是人少力量大，是信息不乱、决策留痕、反馈跟到底。

## 3. AI 协作模式：Spec 驱动加工作流加专家 Agent

【配图：01-交付体系一页卡.png】


AI 协作模式是这套方法论的发动机。很多人用 AI 写代码，是"想到什么问什么"——每次重新写 Prompt，每次从零开始，AI 的输出质量全看 Prompt 写得好不好。这种模式效率低、质量不稳定，而且无法复用。

我们的做法是 Spec 驱动开发（SDD）。每个功能模块，先写四份文档：分析文档（可行性分析、技术选型、风险评估）、需求文档（验收标准、Given/When/Then 场景）、设计文档（API 设计、数据库设计、架构设计）、任务文档（分步实施清单、每步的具体操作）。四份文档写完、审核通过后，再让 AI 按任务文档逐步实施。

Spec 驱动的好处是什么？第一，先想清楚再动手，避免 AI 跑偏——AI 写代码时不需要做技术决策，只需要按设计文档实现，零返工重构。第二，文档是单一事实源——前端看需求文档理解功能，测试看验收标准写用例，甲方看设计文档评审方案，AI 看任务文档写代码，所有人对齐到同一份文档。第三，可复用——Spec 文档沉淀下来，后续做类似功能可以直接参考。

光有 Spec 还不够，还要有工作流自动路由。我们建立了 11 条工作流 SOP，覆盖从需求调研到生产问题处理的完整生命周期：需求调研、原型驱动、PRD 输出、设计决策、代码开发、一致性检查、文档翻译、反馈跟进、生产问题处理等。AI 根据用户意图自动匹配工作流，按 SOP 标准化执行，不需要每次重新写 Prompt。

再加上专家 Agent 并行评审。我们定义了 7 个专家 Agent：架构专家（审查架构合规性）、代码审查员（审查代码质量和安全）、前端专家（审查 React 代码）、多租户专家（审查多租户实现）、产品专家（审查 PRD 完整性）、验证器（三层校验清单逐项审查）。AI 写完代码后，多个专家 Agent 并行评审，从不同角度挑问题，评审通过后才提交。

还有记忆系统。我们建立了 49 条跨会话持久记忆，覆盖用户偏好、项目知识、工程实践、工具参考。AI 每次启动自动加载记忆，不需要重复解释"我们项目的命名规范是什么""这个业务概念是什么意思"。

这套体系让 AI 从"每次从零开始的聊天机器人"变成"有规则、有流程、有专家、有记忆的工程化流水线"。一个多月交付十多万行代码，靠的就是这套流水线。

Spec 驱动的核心不是文档多，是先想清楚再动手，让 AI 不跑偏。

## 4. 质量保障：三层 Validator 加 SonarQube 门禁

AI 写代码有一个特点：速度快，但质量参差不齐。有时候生成的代码很漂亮，有时候有明显的 Bug 或安全漏洞。如果没有质量保障，AI 写得越快，技术债积累得越快。

我们的质量保障体系有三层。

【配图：04-质量三层门禁.png】

第一层是三层 Validator 自检。AI 写完代码后，在提交前自动跑三层校验：编码规范校验（命名、异常处理、日志、API 规范、数据库规范、缓存规范、消息队列规范）、合规校验（安全规则、输入校验、鉴权、密码处理）、架构约束校验（分层架构合规、依赖方向、模块边界）。三层校验逐项检查，任何一项不通过就不允许提交。

第二层是 SonarQube 质量门禁。代码提交后，CI 流水线自动跑 SonarQube 静态代码分析，检查代码异味、Bug、安全漏洞、测试覆盖率。我们设定了严格的门禁——新增代码零 Bug、零安全漏洞、代码异味在可接受范围内、Service 层测试覆盖率不低于 85%、Controller 层不低于 70%。门禁不通过，CI 直接失败，代码合不进去。

第三层是人工审核。AI 的所有产出，无论是代码还是文档，都要经过 FDE 审核。FDE 看什么？看技术决策对不对、看业务逻辑有没有遗漏、看边界条件有没有考虑、看代码可读性好不好。AI 能写出"能跑的代码"，但"能跑"和"可维护"之间还有距离，这个距离靠人来补。

这套质量保障体系的效果怎么样？CI 一次通过率超过九成——也就是说，AI 写的代码经过三层 Validator 自检后，提交到 CI 上九成以上能一次通过。SonarQube 的 Issue 数从最初的近百个，逐步降到零。测试覆盖率稳定在门禁线以上。

这里有一个关键认知：质量保障不是"写完代码再检查"，是"在写代码的过程中就把质量内建进去"。三层 Validator 是 AI 写代码时的实时约束，SonarQube 是提交后的自动验证，人工审核是最终的质量把关。三层叠加，AI 写得快但质量不打折。

AI 写得快不可怕，可怕的是没有质量门禁——快和稳之间，靠工程化体系搭桥。

## 5. 文档体系：PRD、Spec、设计、SOP 全类型覆盖


很多团队做项目，文档是"写完代码再补"的附属品——代码跑通了，随便写个 README 应付了事。但在 FDE 加 AI 的协作模式下，文档不是附属品，是核心。

为什么？因为 AI 协作的基础是文档。

【配图：05-五类文档受众矩阵.png】AI 看 PRD 理解需求，看 Spec 知道怎么实现，看设计文档知道技术决策，看 SOP 知道操作流程。没有文档，AI 每次都要从零开始问"你要做什么""怎么做"，效率回到原点。

我们的文档体系覆盖全类型。

PRD 文档：4 个 Epic、10 个 Story，每个 Story 有功能描述、验收标准（Given/When/Then 场景）、优先级、依赖关系。PRD 是给产品和测试看的，用业务语言写，不涉及技术实现。

Spec 文档：13 个功能模块，每个模块 4 份文档——分析、需求、设计、任务。Spec 是给开发和 AI 看的，用技术语言写，具体到 API 路径、数据库表结构、字段定义、分步实施清单。

设计文档：5 份架构设计文档，覆盖整体架构、多租户设计、数据模型、API 设计、安全设计。设计文档是给甲方评审和团队对齐用的，讲清楚"为什么这么设计"而不只是"设计成什么样"。

SOP 文档：11 条工作流 SOP，每条 SOP 有触发场景、执行步骤、产出物、质量标准。SOP 是给 AI 和团队成员看的，标准化操作流程，减少"每个人做法不一样"的混乱。

还有大量会议纪要、测试脚本、术语表、变更记录。

这些文档不是"写完就扔"，是在项目中反复使用的。前端同事看 PRD 理解需求，测试同事看验收标准写用例，甲方看设计文档评审方案，AI 看 Spec 生成代码，FDE 看 SOP 管理工作流。文档是整个项目的单一事实源——任何争议，回到文档找答案；任何变更，先改文档再改代码。

文档体系还有一个长期价值：可复用。项目结束后，这些文档沉淀为知识库。后续做类似项目，PRD 模板、Spec 结构、SOP 流程都可以直接复用，不需要从零开始。这就是知识复利——一次投入，多次收益。

文档不是交付的附属品，是交付本身——没有文档的 AI 协作，每次都是从零开始。

## 6. 踩坑复盘：什么有效、什么需要注意


一个多月的项目做完，我做了完整的复盘。哪些做法有效，哪些做法有问题，都记录下来。这部分是最有价值的——成功的经验可以复用，踩过的坑可以避免。

先说什么有效。

【配图：06-复盘五有效三注意.png】

第一，Spec 先行最有效。analysis→requirements→design→tasks 四文档流程，确保 AI 不跑偏。项目中没有出现大规模返工重构，因为技术决策在设计阶段就想清楚了，AI 只负责按设计实现。零返工重构是 Spec 先行的直接成果。

第二，Validator 三层自检有效。编码规范加合规加架构约束，作为 AI 代码的安全网。CI 一次通过率超过九成，说明大部分问题在提交前就被 Validator 拦住了。如果没有 Validator，这些问题会流到 CI 甚至生产环境，修复成本成倍增加。

第三，Memory 系统有效。49 条持久记忆消除重复解释。项目中期，AI 已经能自动记住命名规范、业务概念、工程实践，不需要每次重新解释。这省下的时间看起来不多，但累积起来很可观——每次会话省 5 分钟解释，上百次会话就是好几小时。

第四，Workflow 路由有效。意图识别加 SOP 标准化，减少 Prompt 编写成本。遇到重复性任务（需求分析、代码审查、文档生成），AI 自动匹配工作流，按 SOP 执行，不需要每次写详细的 Prompt。

第五，问题结构化归档有效。每个问题记录"现象、分析、修复"三件套，grep 可检索，30 秒定位。项目后期遇到类似问题，直接搜归档记录，不需要重新排查。

再说什么需要注意。

第一，Plan 模式频率要控制。单文件微调不需要 Plan，避免过度设计。项目早期有几次，我让 AI 对一个简单的字段修改做了完整的 Plan 分析，花了十几分钟，实际上直接改两分钟就完了。后来定了规则：涉及多文件、多模块的改动才用 Plan，单文件微调直接改。

第二，Token 消耗要有意识。长会话及时压缩，减少缓存失效。项目中 AI 的 Token 消耗不小，其中有一部分是不必要的——会话太长导致上下文溢出、重复加载大文件、缓存失效后重新读取。后来养成习惯：会话超过一定长度就压缩，大文件用引用不粘贴正文。

第三，模型切换成本要注意。不同 AI 工具的规则文件格式不兼容——Claude Code 用 CLAUDE.md，GitHub Copilot 用 .github/copilot-instructions.md，格式和机制都不一样。甲方用 Copilot，我们用 Claude Code，AI 工程化资产不能直接迁移，交付时只提供 PRD、设计、代码、测试、SOP 等中性产出。如果后续要换工具，规则体系要重建。

复盘的价值不是总结成功，是把踩过的坑变成下次的护栏。

## 7. 方法论总结：可复用的五条经验


讲完了团队架构、AI 协作、质量保障、文档体系、踩坑复盘，最后把这套方法论浓缩为五条可复用的经验。

【配图：07-五条可复用经验.png】

第一条，Spec 先行。任何功能，先写分析、需求、设计、任务四份文档，再动手写代码。不要觉得"写文档浪费时间"——写文档花的时间，会在零返工中十倍赚回来。Spec 先行的核心是"先想清楚再动手"，这个原则对人对 AI 都适用。

第二条，质量内建。不要"写完代码再检查质量"，要在写代码的过程中就把质量约束加进去。三层 Validator 自检是 AI 的实时约束，SonarQube 是提交后的自动验证，人工审核是最终把关。三层叠加，快和稳可以兼得。

第三条，文档即事实。文档不是附属品，是单一事实源——任何争议回到文档找答案，任何变更先改文档再改代码。PRD 给产品看，Spec 给开发看，设计给甲方看，SOP 给 AI 看，每种文档有明确的受众和目的。文档沉淀下来就是知识库，一次投入多次收益。

第四条，AI 是团队成员，不是工具。把 AI 当成"虚拟团队成员"来管理——给它定规则（规则文件）、定流程（工作流 SOP）、配专家（专家 Agent）、建记忆（持久记忆）。它能独立完成代码生成、文档撰写、质量扫描，但所有产出要经过人的审核。FDE 是 AI 的"项目经理"，定方向、审产出、把质量关。

第五条，复盘即复利。每个项目做完都要复盘——什么有效、什么需要注意、什么可以改进。复盘记录沉淀下来，就是下一个项目的护栏和加速器。知识复利的关键不是"学了多少"，是"沉淀了多少可复用的经验"。

这五条经验，不需要等"大项目"才用。你现在做的个人项目、工作中的小需求，都可以用 Spec 先行、质量内建、文档即事实的方法来做。AI 是团队成员的理念，从你第一次给 AI 写规则文件开始。复盘即复利，从你第一次记录踩坑经验开始。

我自己就是这样。做这个项目之前，我没有完整的 AI 工程化体系。但项目逼着我把 Spec、工作流、Validator、Memory 一样一样建起来。做完项目，这套体系就沉淀下来了。后续做其他项目，直接复用，效率比第一次高得多。

方法论的价值不是"项目做完了"，是"下一个项目能做得更快更好"。

## 8. 核心结论（5条）

1. 一个多月、小团队、十多万行代码，靠的不是 AI 多聪明，是 Spec 驱动、工作流路由、专家 Agent 评审、三层质量门禁的工程化方法论
2. 团队架构核心是 FDE 统一对接——前端、测试、甲方的所有信息通过 FDE 中转，AI 作为"虚拟团队成员"全程参与，FDE 是 AI 的项目经理
3. AI 协作的核心是 Spec 驱动开发——先写分析、需求、设计、任务四份文档再实施，零返工重构；配合 11 条工作流 SOP 和 7 个专家 Agent，AI 从聊天机器人变成工程化流水线
4. 质量保障靠三层 Validator 自检加 SonarQube 门禁加人工审核，CI 一次通过率超过九成，SonarQube 从零 Issue 降到零——快和稳可以兼得
5. 五条可复用经验：Spec 先行、质量内建、文档即事实、AI 是团队成员、复盘即复利——不需要等大项目，从个人项目就能落地
