# AI 工程师/FDE 招聘：会调 Prompt 不够，能去客户现场聊才是硬门槛

【配图：00-引子图-面试框架.png】

**行途导读**

前段时间，我作为技术面试官，面试了几位全栈交付工程师（FDE 方向）候选人。多轮面试后，我把考察维度从"AI 工程化优先"调整为"客户现场沟通 + Java 双硬门槛"。最终定型为 3 硬门槛 + 4 核心 + 2 加分。这套方法论对你招人或自查都有用。

先说结论：FDE 的考察维度是 3 硬门槛 + 4 核心 + 2 加分。三个硬门槛是客户现场沟通能力、Java 后端主栈、能到客户现场——任一不通过直接淘汰。四个核心考察维度是商务沟通能力、外部客户对接经验、Java 后端技术深度、全生命周期交付意识。两个加分项是 AI 工程化实践和前端能力。AI 工程化从"核心"降为"加分"，因为市场上能同时满足"Java 深度 + 客户现场沟通 + 驻场意愿"的人已经稀缺，AI 工程化反而是可以培养的。

## 为什么考察维度从"AI 优先"变成"沟通 + Java 双硬门槛"

一开始定的是"AI 工程化优先"，面了几位候选人后发现硬门槛不过关的人 AI 再强也没用。调整为"客户现场沟通 + Java 双硬门槛"，AI 工程化降为加分项。

先讲一个面试中的真实教训。

我面的第一位候选人，AI 工程化实践很丰富——日常用 AI 工具做代码审查、测试生成、文档撰写，还搭建过 AI 代码生成流水线。技术视野也不错，对 AI 辅助开发有自己的理解。我一开始觉得这个人不错，AI 时代的 FDE 就该这样。

但面到 Java 后端技术深度时，问题来了。Spring Boot 自动配置原理说不清楚，设计模式只能举教科书例子没有实际项目经验，慢 SQL 排查没有实际优化案例，Redis 三穿只知道概念没处理过。我追问"你在项目中遇到过最复杂的技术问题是什么"，他讲的是前端框架选型，不是后端技术难题。

这位候选人的 AI 工程化确实好，但 Java 后端深度不够。而 FDE 项目的客户系统大多是 Java 技术栈（Spring Boot + MyBatis + MySQL），要在现有系统上做改造，不是从零搭建。主栈不对，补课周期不可控——你不能让客户等你学完 Java 再开始干活。

第二位候选人，Java 后端深度够，AI 工程化也有实践。但面到客户现场沟通时，问题来了。我模拟了一个需求沟通场景——"假设你到客户现场，面对一个不懂技术的业务方，他说'我要一个能自动分析销售数据的功能'，你怎么接？"这位候选人的回答全是技术术语："我们可以用 RAG 架构，把销售数据向量化，然后用大模型做检索增强生成……"业务方根本听不懂。

我追问"能不能用业务方听得懂的话解释"，他想了半天，说"就是让 AI 帮你查数据"。这个翻译太粗糙了——没有澄清需求、没有确认场景、没有对齐期望。FDE 在客户现场的核心能力就是把技术语言翻译成业务语言，把模糊需求翻译成可交付方案。这个能力不过关，到了客户现场连需求都拿不到。

面了几位之后，我的结论很清晰：AI 工程化是加分，不是入场券。硬门槛不过关的人，AI 再强也做不了 FDE。所以我把考察维度从"AI 优先"调整为"客户现场沟通 + Java 双硬门槛"，AI 工程化降为加分项。

个人观点：FDE 招人不是招"AI 用得好的人"，是招"能在客户现场把事办成的人"。

## 三个硬门槛：任一不通过直接淘汰

【配图：02-三个硬门槛.png】

三个硬门槛是客户现场沟通能力、Java 后端主栈、能到客户现场。验证方法分别是模拟需求沟通、简历筛选即判定、直接确认。任一不通过，不进入后续面试。

硬门槛一：客户现场沟通能力。

考察什么？FDE 要跟客户面对面沟通需求、讲解方案、处理冲突。技术再好，沟通不过关，连需求都听不明白，更别说翻译了。这里的"沟通"不是"能说话"，是能把技术方案讲清楚、把客户需求听明白、在冲突中把事推下去。

怎么验证？模拟需求沟通场景。我会给候选人一个具体场景——"客户说'我要一个能自动生成报表的功能'，你怎么接？"看候选人能不能先澄清需求（什么报表？给谁看？多久一次？数据从哪来？），能不能用业务语言解释技术方案，能不能处理客户的不合理期望。

典型好回答：先问五个问题——报表的用途是什么、受众是谁、更新频率、数据来源、有没有现成模板。然后用业务语言解释："这个功能可以帮您把每周花两小时整理的报表，变成一键生成。我们先从您最常用的一张报表开始做，跑通了再扩展。"

淘汰信号：满口技术术语（RAG、向量数据库、大模型微调），业务方根本听不懂；不澄清需求直接给方案；客户说什么都答应，不会管理期望。

硬门槛二：Java 后端主栈（Spring Boot / MyBatis / MySQL）。

考察什么？客户系统大多是 Java 技术栈，要在现有系统上做改造。Node.js、Python 再熟练，到了客户现场也得补课，补课周期不可控。

怎么验证？简历筛选即判定。看候选人最近两到三年的主力技术栈是不是 Java。如果主栈是 Node.js 或 Python，按后端补课成本重新评估——不是完全不行，但风险很大。

典型好回答：最近三年主力是 Spring Boot + MyBatis + MySQL，做过企业级应用开发和改造，熟悉 Spring 生态、数据库设计、中间件使用。

淘汰信号：主栈是 Node.js/Python，Java 只是"了解"；最近一年没写过 Java；只会用 Spring Boot 写 CRUD，不懂自动配置原理、设计模式、性能优化。

硬门槛三：能到客户现场（接受出差/驻场）。

考察什么？FDE 的核心就是"在现场"。不能驻场就不是 FDE——远程做 AI 落地，就像隔着玻璃修机器，看得到问题但碰不到零件。

怎么验证？直接确认。问"这个岗位需要到客户现场驻场，可能连续几周甚至几个月，你能接受吗？"

典型好回答：能接受，之前有过驻场或出差经验，知道现场工作的节奏和挑战。

淘汰信号：犹豫、说"尽量"、要求"每周不超过两天"；完全没有出差经验且明显抗拒。

个人观点：硬门槛的意义不是筛掉多少人，是确保进来的人能在客户现场活下来。

## 核心维度一：商务沟通能力——把技术语言翻译成业务语言

【配图：03-四个核心维度.png】

商务沟通不只是能说话，是能把技术语言翻译成业务语言。面对不懂技术的业务方，能不能把方案讲清楚，是 FDE 的关键能力。

考察什么？商务沟通能力的核心是"翻译"——把技术方案翻译成业务方能理解的语言，把业务方的模糊需求翻译成技术能实现的方案。这不只是表达能力，是理解能力加共情能力加表达能力的综合体。

FDE 在客户现场每天都要做翻译。跟甲方 PO 沟通时，要把"我们用了多租户架构、DB-per-Tenant 模式"翻译成"每个客户的数据是独立的，互不影响"；跟业务方沟通时，要把"这个需求需要改数据库表结构、加索引、写迁移脚本"翻译成"这个改动需要一周时间，因为要确保现有数据不丢失"。

怎么验证？两个方法。第一，场景模拟——给候选人一个技术方案，让他用业务方听得懂的话解释。第二，追问经历——"你过去有没有跟非技术人员沟通技术方案的经历？对方听懂了吗？你怎么判断他听懂了？"

典型好回答：有类比能力，知道什么信息该说什么不该说。比如解释"为什么需要一周"，会说"这个改动涉及三个系统的数据对齐，就像搬家时要把三个房间的东西整理到一起，不是把箱子搬过去就行，还要拆开、分类、归位"。会观察对方的反应，确认对方真的理解了，而不是自己说完就完了。

淘汰信号：满口技术术语，无法切换频道；觉得"业务方就该懂技术"；解释时只说"怎么做"不说"为什么"；不会管理客户期望，客户说什么都答应。

这里有一个常见误区：很多人觉得商务沟通就是"性格外向、能说会道"。其实不是。我见过性格内向但商务沟通极强的人——他们话不多，但每句话都说到点子上，能精准捕捉对方的需求和顾虑，用最简洁的语言把方案讲清楚。也见过性格外向但商务沟通极差的人——话说了一大堆，对方还是没听懂，而且不该说的信息也说了，给自己挖坑。

个人观点：商务沟通的核心不是能说，是让对方听懂并且认同。

## 核心维度二：外部客户对接经验——在客户现场独当一面

有没有直接对接过外部客户？遇到过需求不清晰、客户反复变更的情况吗？怎么处理的？FDE 要在客户现场独当一面，不只是技术好，还要能跟非技术人员沟通。

考察什么？外部客户对接经验的核心是"独当一面"——不只是技术好，还要能跟非技术人员沟通、处理需求变更、管理客户期望、在冲突中推进项目。内部项目和外部客户项目的区别很大：内部项目需求相对清晰、变更有流程、沟通有组织保障；外部客户项目需求模糊、变更是常态、沟通全靠自己。

怎么验证？三个追问。第一，"你过去有没有直接对接外部客户的经历？是技术对接还是需求对接？邮件为主还是会议为主？"第二，"有没有遇到过需求不清晰、客户反复变更的情况？你怎么处理的？"第三，"客户提出一个不合理的需求，你怎么拒绝？"

典型好回答：有直接对接外部客户的经历，不只是技术对接，还参与过需求沟通和方案讲解。遇到需求变更时，不是直接拒绝或直接答应，而是先理解变更背后的业务原因，再评估影响范围，然后给出方案——"这个需求可以做，但会影响当前排期，您看是加人还是延期？"拒绝不合理需求时，不是说"做不了"，而是说"这个方案有 XX 风险，我建议换一种方式，效果一样但风险小很多"。

淘汰信号：只有内部项目经验，没对接过外部客户；客户说什么都答应，不会管理期望；遇到需求变更就抱怨，不会主动找解决方案；拒绝需求时生硬，容易得罪客户。

这里有一个关键判断：候选人能不能说清自己在客户对接中的边界。有些人说"我对接过客户"，但仔细追问发现只是"参加过客户会议，没说过话"或者"客户提了需求，我转给产品经理了"。FDE 需要的是"独立对接"——自己跟客户聊需求、自己讲方案、自己处理冲突，而不是"在场但不发言"。

个人观点：外部客户对接经验的核心不是"见过客户"，是"能在客户现场独当一面"。

## 核心维度三：Java 后端技术深度——交付的基本功

Java 后端技术深度是 FDE 交付的基本功。Spring Boot 自动配置原理、设计模式实际应用、慢 SQL 排查、Redis 三穿、消息队列可靠性——这些不过关，做不了交付。

考察什么？Java 后端技术深度是 FDE 交付的基本功。FDE 项目通常是在客户现有系统上做改造，不是从零搭建。客户系统是 Java 技术栈，你要能看懂现有代码、能在上面加功能、能排查性能问题、能处理中间件故障。这些都需要 Java 后端的技术深度，不是"会写 CRUD"就行。

怎么验证？必问五个方向。

第一，Spring Boot 原理。"说一下 Spring Boot 自动配置原理？自定义过 Starter 吗？"看候选人是不是真的理解 Spring Boot 的工作机制，还是只会用注解。

第二，设计模式。"你用过哪些设计模式？举一个实际项目中的例子。为什么选这个模式？有没有做过取舍？"看候选人是不是真的在项目中用过设计模式，还是只背过教科书定义。

第三，数据库。"慢 SQL 怎么排查？说一个实际优化案例。"看候选人有没有实际的性能优化经验，explain 关注什么，索引怎么加。

第四，中间件。"Redis 用过哪些场景？缓存三穿（穿透/击穿/雪崩）处理过吗？用过消息队列吗？怎么保证消息可靠性？"看候选人对常用中间件的理解深度。

第五，加分问。分布式事务、分库分表、K8s 部署运维——不答不扣分，答了加分。

典型好回答：每个问题都能结合实际项目经验，讲清楚"遇到了什么问题、怎么分析的、怎么解决的、效果如何"。不是背概念，是讲经历。

淘汰信号：只会背概念，没有实际项目经验；Spring Boot 只会用注解，不懂自动配置原理；设计模式只能举教科书例子；慢 SQL 排查没有实际案例；Redis 三穿只知道概念没处理过。

这里有一个判断技巧：好的候选人会被追问——每个问题能引出更多细节，你越问越深入，他能一直讲下去。差的候选人会让你换话题——讲完概念就没了，再追问就说"这个没深入研究过"。面试时间有限，Java 后端深度是核心，不压缩时间。

个人观点：Java 后端技术深度不是"会写代码"，是"能在客户现有系统上把事办成"。

## 核心维度四：全生命周期交付意识——从需求到上线负责到底

FDE 不是"拿需求写代码"，要从需求沟通、PRD 编写、方案设计、开发测试、部署上线到运维优化，从头到尾负责。能把模糊需求变成可交付方案，比写一段漂亮代码值钱得多。

考察什么？全生命周期交付意识的核心是"负责到底"——不只是写代码，还要参与需求分析、方案设计、测试、部署、运维。FDE 在客户现场，客户不会把需求拆得清清楚楚给你，你要自己从模糊的业务描述中提炼需求、写 PRD、做方案、开发、测试、上线，一条龙负责到底。

怎么验证？两个问题。

第一，"从接到需求到代码上线，你一般经过哪些步骤？"追问："你有没有自己写过 PRD 或技术方案文档？""你参与过需求分析吗？还是拿到的都是已排好的需求？""谁来做测试？你有没有写过自动化测试？"

第二，"说一个你从 0 到 1 主导的项目（不是你参与的）。"追问："方案是你写的吗？谁评审的？""团队多少人？你怎么分工的？"关键判断：能不能说清自己在项目中的边界——哪些是你做的，哪些是别人做的。

典型好回答：能完整描述从需求到上线的全流程，不只是"写代码"。自己写过 PRD 或技术方案，参与过需求讨论，写过测试用例，做过部署上线。从 0 到 1 主导过项目，能说清自己的角色和边界，不夸大也不缩小。

淘汰信号：只会说"拿到需求写代码，写完提测"；没写过 PRD 或技术方案；没参与过需求分析；从 0 到 1 主导的项目讲不清楚，追问后发现其实是"参与"不是"主导"；说不清楚自己在项目中的边界，什么都是"我们团队做的"。

这里有一个常见误区：很多技术人觉得"全生命周期交付"就是"什么都干"。其实不是。全生命周期交付的核心是"对结果负责"——你不一定要自己写测试用例，但你要确保测试覆盖到位；你不一定要自己做运维，但你要确保系统上线后能稳定运行。负责到底，不是事必躬亲。

个人观点：全生命周期交付意识的核心不是"什么都干"，是"对结果负责到底"。

## 两个加分项：AI 工程化实践和前端能力

AI 工程化和前端能力是加分项，不是核心。AI 工程化可培养——市场上硬门槛过关的人已经稀缺，AI 可以入职后练。前端能力能写是加分，不会不影响录用。

【配图：04-两个加分项.png】

加分项一：AI 工程化实践。

为什么是加分不是核心？因为市场上能同时满足"Java 后端深度 + 客户现场沟通能力 + 驻场意愿"的人已经稀缺，AI 工程化反而是可以培养的。一个 Java 深度够、沟通能力强的人，入职后花一两个月就能把 AI 工程化练起来；但一个 AI 工程化强、Java 深度不够的人，补 Java 可能要半年，而且客户等不起。

怎么验证？有经验的问："日常用哪些 AI 工具？除了写代码，有没有用它做 review、测试、文档？"加分验证：知不知道 AI 工程化的目录结构（规则、工作流、专家 Agent、技能）？有没有搭建过 AI 代码生成流水线？无经验的问："你对 AI 辅助开发怎么看？愿意投入多深？"期望是有兴趣、有学习意愿、有技术好奇心。

补充一个行业里正在用的做法：AI 笔试。有家公司招 FDE 时加了一轮 AI 实操笔试——给一台电脑，让候选人在 30 分钟内用 AI 工具完成一个小功能（比如写一个数据清洗脚本），过程中全程监控防作弊。这不是考 AI 用得多熟，是看候选人在真实压力下能不能让 AI 产出可用的东西。我们暂时没做这轮，但值得借鉴。

典型好回答：日常用 AI 工具不只是写代码，还做代码审查、测试生成、文档撰写。对 AI 工程化有自己的理解——知道规则文件、工作流 SOP、专家 Agent 的概念，甚至自己搭建过。对 AI 辅助开发有积极态度，愿意深入学习。

不加分但不淘汰：完全不用 AI 工具，且对 AI 辅助开发持抵触态度，认为"AI 不可靠""都是玩具"。这种人不是不能用，但培养成本高。

加分项二：前端能力。

为什么是加分？FDE 项目后端工作量通常大于前端，前端有专门的前端同事负责。但 FDE 能写前端的话，在小团队里更灵活——前端同事忙不过来时可以搭把手，简单页面可以自己搞定，跟前端同事沟通时也更顺畅。

怎么验证？"你说会 React/Vue，你独立写过的最大前端项目是什么？几个页面？状态管理用的什么？"

典型好回答：能独立写完整的前端页面，理解组件化、状态管理、路由等概念，有实际项目经验。

不加分但不淘汰：不会前端，或只会写简单的 HTML/CSS。FDE 项目后端为主，不会前端不影响录用。

个人观点：加分项是硬门槛过了之后的放大器——门槛没过，加分再多也接不住。

## 面试节奏控制和决策矩阵

面试 40 到 50 分钟，节奏是：开场破冰（客户现场沟通模拟）→ 外部客户对接经验 → Java 后端技术深度（最大权重）→ 全生命周期交付意识 → 加分项 → 反问。决策矩阵以硬门槛为一票否决。

面试节奏控制很重要。40 到 50 分钟，时间分配要有侧重。

【配图：05-面试时间分配.png】

开场破冰 3 分钟：先做客户现场沟通模拟——让候选人用业务语言解释一个技术方案，或者模拟需求沟通场景。这是硬门槛第一关，1 分钟就能判断沟通能力行不行。不行的话，后面的技术面可以缩短，但还是要走完流程给候选人反馈。

外部客户对接经验 5 分钟：追问有没有直接对接过外部客户、怎么处理需求变更、怎么拒绝不合理需求。

Java 后端技术深度 15 分钟：最大权重，不压缩时间。Spring Boot 原理、设计模式、数据库、中间件，四个方向必问，加分问看时间。

全生命周期交付意识 8 分钟：从需求到上线的全流程、有没有写过 PRD、从 0 到 1 主导的项目。

加分项 5 分钟：AI 工程化和前端能力，快速验证，不占用大量时间。

反问和结束 5 分钟：给候选人提问机会，回答问题，结束面试。

决策矩阵很简单，以硬门槛为一票否决：

- 客户现场沟通 + Java + 驻场，三个硬门槛全过 + 四个核心全过 → 强烈推荐
- 三个硬门槛全过 + 四个核心有一两个待提升 → 推荐，可培养
- 三个硬门槛全过 + 核心能力一般 → 可考虑
- 硬门槛有一个不过 → 不推荐，不管其他维度多强

这里有一个原则：硬门槛是一票否决。客户现场沟通不过关的人，Java 再深、AI 再强，到了客户现场也拿不到需求；Java 主栈不对的人，沟通再好，到了现场也写不了代码；不能驻场的人，其他能力再强，也不是 FDE。

个人观点：面试节奏的核心是"把时间花在最能区分候选人的地方"——Java 深度和客户现场沟通。

## 候选人复盘：新标准下回头看

面了几位候选人后，用新标准回头看，每个人都有短板——要么缺 Java，要么客户现场沟通没验证，要么深度不足。新标准比旧标准更务实：Java + 客户现场沟通是双硬门槛，过了再比深度。

面了几位候选人之后，我用新标准（3+4+2）回头看，发现一个共性：在新标准下，每个人都有短板。

【配图：06-候选人ABC复盘.png】

候选人 A，十年经验，客户现场沟通能力强，外部客户对接经验丰富，但主栈是 Node.js，Java 只是"了解"。新标准下，Java 硬门槛不过关，直接淘汰。旧标准（AI 优先）下，可能会因为"沟通好、有客户经验"而考虑，但实际上到了 Java 客户现场，他写不了代码，只能做沟通，那不是 FDE，是项目经理。

候选人 B，六年经验，AI 工程化实践丰富，技术潜力不错，但 Java 后端深度不足，客户现场沟通没验证。新标准下，Java 硬门槛不过关，客户现场沟通没验证，两个硬门槛有问题。旧标准下，可能会因为"AI 工程化好"而给机会，但实际上 AI 工程化是可以培养的，Java 深度和沟通能力才是硬约束。

候选人 C，五年经验，客户现场沟通能力可以，Java 主栈对路，外部客户对接经验有，但 Java 技术深度不足——Spring Boot 原理说不清楚，设计模式只有教科书例子，慢 SQL 没有实际优化案例。新标准下，硬门槛全过，但核心维度（Java 深度）不足，属于"可考虑，需要培养"。

这三位候选人在旧标准（AI 优先）下，可能会有不同的评价；但在新标准（3+4+2）下，评价很清晰——硬门槛过了吗？核心能力够了吗？加分项有多少？

新标准比旧标准更务实。Java + 客户现场沟通是双硬门槛，过了再比深度。AI 工程化是加分，不是入场券。这个调整不是否定 AI 工程化的价值，是承认一个现实：市场上真正符合 FDE 画像的人非常稀缺，招人要先保硬门槛，再看核心能力，最后才是加分项。

如果你正在考虑转 FDE，用这套维度自查一下：硬门槛过了吗？核心能力够了吗？加分项有多少？答案会告诉你离 FDE 还有多远。

个人观点：FDE 的人才画像很清晰——客户现场能沟通、Java 能交付、对结果负责。AI 工程化是加分，不是核心。

## 核心结论

- FDE 考察维度是 3 硬门槛 + 4 核心 + 2 加分：硬门槛是客户现场沟通能力、Java 后端主栈、能到客户现场，任一不通过直接淘汰
- 四个核心考察维度：商务沟通能力（把技术翻译成业务语言）、外部客户对接经验（在现场独当一面）、Java 后端技术深度（交付基本功）、全生命周期交付意识（对结果负责到底）
- 两个加分项：AI 工程化实践和前端能力。AI 工程化从"核心"降为"加分"，因为硬门槛过关的人已经稀缺，AI 可以入职后培养
- 面试节奏：40-50 分钟，Java 后端深度占 15 分钟（最大权重），客户现场沟通开场即验证，硬门槛一票否决
- 候选人复盘：新标准下每个人都有短板，市场上真正符合 FDE 画像的人非常稀缺；转 FDE 先用这套维度自查，硬门槛优先补齐
